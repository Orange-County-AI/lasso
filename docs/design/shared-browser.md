# Browser tab and the shared browser (`src/web/src/components/BrowserTab.tsx`, `LiveBrowser.tsx`, `src/web/src/lib/cdp.ts`, `src/web/src/lib/browser-url.ts`, `src/browser.go`, `src/browserprofiles.go`, `src/cdpproxy.go`, `src/mcp_browser.go`, `src/mcp_browser_profiles.go`, `src/browsermcp.go`)

Two modes behind one toolbar switch, stored as `ui_state.browser_mode` (`live` | `embed`, default `live`; validated on write, an unknown stored value reads as `live` — `normalizeBrowserMode`). **Live** (labelled **Agent** in the UI, and **Embed** is labelled **Iframe**: the stored values kept their names, the labels say who else sees the page) is a headless Chromium lasso supervises on its own machine, drawn in the tab from a CDP screencast with input forwarded; agents drive the same Chromium over `/cdp`. **Embed** is the iframe the tab always was. The stored preference is not always what is shown: with `GET /api/browser` answering `available:false` (or failing — an older server) the tab shows Embed with a line giving the reason, **without** rewriting the preference, so installing Chromium later brings Live back on its own.

### Embed (unchanged)

A URL bar and an iframe. A bare port (`5173`, `:5173`, `localhost:5173`) resolves to `http://<location.hostname>:<port>`; a schemeless URL gets `https://` except for a loopback host, which gets `http://` (`normalize` in `lib/browser-url.ts`). There is no backend behind the frame: no `/api/preview`, no `tailscale serve` forwards, no Cloudflare wildcard demux (`lasso devproxy`), no Access-cookie priming. All of that existed and was **deliberately removed** — it was a lot of per-deployment wiring (DNS wildcard, tunnel ingress, an Access app, a supervised daemon, a `-preview-public-domain` flag) to work around a browser rule, and the rule wins anyway.

- **What the browser allows is the whole contract.** An HTTPS origin can't frame an `http://` dev server (mixed content) and a public origin can't frame a private/tailnet one (Private Network Access). Both cases are detected and reported in the tab, with open-in-new-tab as the out. Don't reintroduce a tunnel to dodge them.
- `probeReachable` (a `no-cors` fetch), not the iframe's `onLoad`, is the failure signal: a PNA-blocked frame still fires `onLoad` while rendering blank.
- **A site that forbids framing is the one thing the browser can't tell the page** (`src/frameable.go`, `GET /api/frameable`). `X-Frame-Options` and CSP `frame-ancestors` refuse the embed silently — `onLoad` fires, the no-cors probe succeeds, the frame is blank — and both headers are unreadable cross-origin. So lasso fetches the URL server-side and applies the browser's rules for the tab's origin. It is **advisory, not a proxy**: nothing is served through it, only a boolean comes back, and any fetch failure answers `null` and the tab says nothing, since lasso's machine is not necessarily where the browser reaches the page from.

### Live: the shared browser

**It is not the preview tunnel coming back.** That tunnel served the *user's* browser a page from somewhere it could not reach; the shared browser is a whole browser running on lasso's machine, and what crosses the wire is CDP — a screencast out, input events in. Nothing is framed, so none of Embed's three limits apply (mixed content, PNA, `frame-ancestors`), and there is no per-deployment wiring: `/cdp` rides whatever already fronts lasso. The flip side is that it browses **from lasso's machine**: a bare port in Live resolves to `http://localhost:<port>` there (`resolveLive`), and `about:`/`data:`/`file:`/`chrome:` URLs pass through literally instead of growing an `https://`.

- **No Go websocket library, on purpose.** `go.mod` has none and gains none. The Go side is a process supervisor (`browser.go`) plus a reverse proxy (`cdpproxy.go`): `httputil.ReverseProxy` already carries websocket upgrades — it is how `/terminal/` reaches ttyd — so lasso never parses a CDP frame. The Browser tab is **just another CDP client** (`lib/cdp.ts`, the page's native `WebSocket`), a peer of the agents on the same endpoint. That is also why the tab never assumes it is alone: its page list is `Target.setDiscoverTargets`, not a list it keeps. **It shows a tab strip of the selected profile's pages and follows the newest**: a `targetCreated` for a page after discovery has started selects it (the existing pages are announced as `targetCreated` too when discovery begins, hence the `discovered` flag), so an agent opening a page puts the human on it. A closed page falls back to another open one. The strip is what made several pages per profile usable: before it, a second page was one nobody could reach.
- **One socket, to the browser target.** Pages are reached with flat sessions (`Target.attachToTarget` + `flatten:true`), so switching tabs is a detach/attach on the same connection. The screencast is `Page.startScreencast` sized to the canvas × devicePixelRatio, every frame acked; the viewport follows the panel via `Browser.setWindowBounds` (falling back to `Emulation.setDeviceMetricsOverride`). Input maps canvas → page CSS px through the last frame's metadata; ⌘K/⌘I/⌘\ and lasso's other shell chords are left to bubble, editing chords go out carrying the editor command (the platform's key bindings are not consulted for synthetic input), paste goes out as `Input.insertText`. `cdpURL` addresses lasso's **origin**, never the tab's host — there is one shared browser per lasso, whatever host a tab is driving.
- **It streams only while someone can see it.** `BrowserTab` gets `active` from App.tsx (Browser selected and the sidebar open) and Live also watches `document.visibilityState`; inactive, it stops the screencast and **closes the socket**, which is what lets the idle stop fire. On reveal it calls `POST /api/browser {action:"start"}` first if the status says stopped, then reconnects with backoff (`reconnectDelay`, 1s→15s) — the same path that rides out a proxy relaunch.
- **Lazy start, idle stop, and how "idle" is counted.** Chromium launches on the first `/cdp` request, `POST /api/browser {action:"start"}`, or the `shared_browser` tool; `run()` stops it after `-browser-idle` (`LASSO_BROWSER_IDLE`, 15m, `0` = never). A proxied websocket holds `ServeHTTP` for the connection's whole life, so an in-flight counter bracketing `serveCDP` (`begin`/`end`) **is** the live-client count — no websocket bookkeeping needed. The reaper re-checks under the launch semaphore so a client connecting between the look and the stop wins.
- **The endpoint comes from `DevToolsActivePort`, not a fixed port.** `--remote-debugging-port=0` lets the kernel pick (9222 would collide with a second lasso or a Playwright run); Chromium writes `<profile>/DevToolsActivePort` (port, then `/devtools/browser/<id>`) once the socket is bound, which makes the file both the readiness signal and the port. The stale file is deleted before each launch and polled for ≤15s (`browserPortWait`); a process that exits first fails with its stderr summarized — the `:FATAL:` line, not the tail, which is a register dump.
- **`/cdp` is the stable address.** Chromium's browser id changes every launch; bare `/cdp` maps to whatever it is now, `/cdp/devtools/...` and `/cdp/json/...` pass through, and every websocket URL in a `/json` answer is rewritten back through `/cdp` (`ws`/`wss` from `r.TLS` or `X-Forwarded-Proto`, **not** "non-loopback means https" — lasso is routinely plain http on a tailnet). An agent configured once with `--wsEndpoint ws://<lasso>/cdp` survives idle stops, restarts and proxy relaunches. The outbound transport pools by `127.0.0.1:<port>`, unique per launch, so a relaunch can never be served down the old instance's connection.
- **Outbound headers, and why each is touched.** `Host` is rewritten to `127.0.0.1:<port>` — Chromium answers only an IP or `localhost` Host (its DNS-rebinding guard). `Origin` is **deleted** — Chromium ≥111 refuses a websocket whose Origin is not in `--remote-allow-origins`. `Authorization` and `Cookie` are dropped (lasso's credentials are not Chromium's), and `Accept-Encoding` on `/json` so the body can be rewritten.
- **The Origin guard must run before the strip, and it is not optional** (`cdpOriginAllowed`). Deleting Origin switches off Chromium's own cross-site defense, so lasso has to do its job first: any page a user visits may open a websocket to a loopback lasso, and without this it could read, type into and navigate the shared browser. No Origin passes (a CLI/agent client); an Origin passes only when its host:port equals the request's `Host`, or `X-Forwarded-Host` when a front proxy set one (default ports normalized); anything else, `null` included, is 403. Tested — keep it that way.
- **The gate** (`withCDPAuth`): `/cdp` is in `withAuthExcept`'s exempt list like `/mcp`, because its clients are agents carrying a token rather than a browser holding UI_AUTH, and it applies its own rule. `MCP_OAUTH` set → what `/mcp` accepts (lasso bearer token or UI_AUTH basic), and a token's scope must `allows("local")` (`cdpScopeCheck` — otherwise a credential the tool refuses could skip the tool and dial `/cdp` directly); plus, **with UI_AUTH unset**, a same-origin browser request (the Browser tab, which cannot mint a token) passes without one — that configuration already leaves `/terminal/` open to anyone who reaches lasso, and the Origin guard has already refused every other page. Only `UI_AUTH` → basic, which a browser sends on its websocket too, as `/terminal/` relies on. Neither → open, `/mcp`'s trust model. `gate.wrap` (Access) fronts all of it, unchanged.
- **Sharpness is a LAUNCH flag, because the screencast ignores everything else** (`-browser-scale`/`LASSO_BROWSER_SCALE`, default 2 → `--force-device-scale-factor`). `Page.startScreencast` always delivers frames at the page's CSS size: an `Emulation.setDeviceMetricsOverride` scale factor makes the page *render* at 2x (`devicePixelRatio` reads 2) and the frames still arrive at 1x — measured 474x585 for a 474x585 viewport, with or without `maxWidth`, jpeg or png. `Page.captureScreenshot` does honor the override, but it repaints, and a repaint emits screencast frames (measured: two per screenshot), so "sharpen after the stream goes quiet" becomes a loop that flashes between the two images and eats the CPU. Only a scale set at launch reaches the frames (measured 2560x1426 for 1280x713). Layout stays in CSS px for everyone; the cost is raster CPU and 4x-pixel agent screenshots, which is why it is a knob.
- **Headless's window is NOT its viewport.** `--headless=new` keeps 87px of invisible window chrome, so a window sized to the tab's box leaves the page short and the frame letterboxed. `LiveBrowser.fit` reads the gap as `outerHeight - innerHeight` (one snapshot, so it is right at any window size) and sizes the window to the box plus that gap. Two traps it avoids: resizing and then re-reading `innerHeight` answers before the resize lands, i.e. with the PREVIOUS size, which reads as "already correct"; and the gap is kept at module level (`chromeGap`), because a component ref resets on every Live → Embed → Live round trip.
- **The resource cap, and the dbus escape it needed.** Headless Chromium on a GPU-less box software-rasterizes and will take several cores. On linux with `systemd-run` on PATH **and** `XDG_RUNTIME_DIR` set (how `--user` finds the manager — absent under a bare ssh session or a container), it launches as `systemd-run --user --scope --quiet --collect -p CPUQuota=… -p MemoryHigh=… -- env DBUS_SESSION_BUS_ADDRESS=disabled: <chrome> …` (`-browser-cpu`/`LASSO_BROWSER_CPU` 200%, `-browser-mem`/`LASSO_BROWSER_MEM` 2G; `off` or empty lifts one, both off = no scope). `--scope` execs in place, so the pid lasso holds is Chromium's and the process-group kill and `Pdeathsig` still reach it. **The `env DBUS_SESSION_BUS_ADDRESS=disabled:` is load-bearing:** given a session bus, Chromium's browser process moves itself into an `app-org.chromium.Chromium-<pid>.scope` of its own (for the XDG portal) — an uncapped one, taking every process it launches afterwards out from under the quota; measured, only the zygote-forked renderers stayed capped. It is set only inside the scope, because systemd-run itself needs the bus. A capped launch that fails retries once uncapped (an uncapped browser beats none); `status().capped` says which happened.
- **Lifecycle backstops.** Own process group (`Setpgid`) so a stop takes renderers and zygote with it (SIGTERM, SIGKILL after 3s); `Pdeathsig: SIGTERM` on linux so a `kill -9` of lasso does not leave a browser burning cores; the shutdown path stops it synchronously after in-flight requests drain. `browserEnv` strips `UI_AUTH`, `MCP_OAUTH` and `LASSO_MCP_TOKEN` from its environment — any exploited renderer's `/proc/<pid>/environ` would otherwise hold them.
- **The profile** is `<lassoDir()>/browser-profile` (`LASSO_DIR`-aware). Cookies and logins persist; **open tabs do not** — `Default/Sessions` is deleted before every launch, because Chromium otherwise restores the last run's tabs on top of its `about:blank`, leaving one more blank tab per launch and showing every page twice after a proxy relaunch (which reopens pages itself). So an idle stop closes the tabs, which is what "nobody is using it" means. Everything logged into this profile is reachable by every client that can reach `/cdp`.
- **A second lasso sharing the data dir is refused, not killed** (`reclaimProfile`). Chromium's `SingletonLock` would make a second launch hand its URL to the first and exit (reading as a crash), so lasso keeps `lasso-browser.pid` in the profile: Chromium's pid, then the owning lasso's. A live Chromium (cmdline naming this profile — `/proc`, or `ps` on a Mac) whose lasso is gone is an orphan and is stopped; one whose lasso is alive belongs to another instance (a dev build beside prod) and the launch fails naming `LASSO_DIR` as the fix, rather than pulling a browser out from under that instance's agents.
- **Binary resolution** (`resolveBrowserBinary`, first hit wins; the search space is a struct so tests fake it): `-browser`/`LASSO_BROWSER` (a path must exist, a name must be on PATH — an explicit choice that fails is **reported**, never silently replaced; `off` disables the feature); PATH `chromium`, `chromium-browser`, `google-chrome-stable`, `google-chrome`, `chrome`; the newest `~/.cache/ms-playwright/chromium-<build>/chrome-linux*/chrome` by **numeric** build; on darwin the Chrome and Chromium app bundles.
- **`No usable sandbox!` is named, not worked around.** Ubuntu 23.10+ (`kernel.apparmor_restrict_unprivileged_userns=1`) lets only binaries with an AppArmor profile create the user namespaces Chromium's sandbox needs; Playwright's and hand-unpacked builds have none. `launchFailure` recognizes it and says what to do — a packaged Chrome/Chromium (Ubuntu ships profiles for those paths), an AppArmor profile granting `userns`, or knowingly `LASSO_BROWSER_ARGS=--no-sandbox`. Adding `--no-sandbox` automatically would quietly run every page an agent opens with lasso's full privileges; it is added only as root, where Chromium refuses to start without it.
- **It does not announce itself as a bot.** Headless Chrome sends `HeadlessChrome/<v>` in its user agent and reads `navigator.webdriver === true`, and bot checks (Cloudflare Turnstile) refuse that browser outright — including for the human clicking "I'm human" by hand in the Browser tab. So every launch gets `--disable-blink-features=AutomationControlled` and `--user-agent=` the UA a headed Chrome of the SAME version sends (`browserUserAgent`: `<bin> --version`, reduced form `Chrome/<major>.0.0.0`, cached per binary; skipped when `LASSO_BROWSER_ARGS` sets its own). The client-hint brands already read Chromium/Google Chrome. CDP is unaffected.
- **Proxy** (`settings.browser_proxy`, `POST /api/browser/proxy`, Settings → General, and per profile). A comma-separated FALLBACK list is Chromium's own `--proxy-server` syntax and is passed through: `socks5://127.0.0.1:1080,direct://` uses the proxy and connects directly when it refuses; `direct://` only last. Chromium then treats a failed proxy as bad for ~5 minutes, so traffic stays direct for a while after the proxy comes back (a profile restart clears it). Each entry: `validateBrowserProxy` accepts exactly `socks5`/`socks4`/`http`/`https` `://host[:port]` — no `socks5h` (curl's spelling; Chromium's socks5 already resolves DNS on the proxy), no userinfo (Chromium cannot authenticate to SOCKS and `--proxy-server` ignores HTTP credentials), no path. `--proxy-server` is read once, so a change while running relaunches: collect `/json/list` page URLs, restart, `PUT /json/new?<url>` each (GET is refused since Chromium 111), close the launch's own `about:blank` by the id taken **before** reopening, and report "reopened N of M" in `status().note`. A stored value that no longer validates launches direct and logs why instead of wedging the feature.
- **`/api/browser*` are ordinary UI routes** behind UI_AUTH (status, start/stop/restart, proxy). Settings and the tab share one React Query entry (`qk.browser`), so a start in one shows in the other.
- **`shared_browser` MCP tool** (`mcp_browser.go`; `lasso mcp shared-browser` for free). It does not drive the browser — `/browser-mcp` and CDP clients do that — it starts it (`start` defaults true; it `touch()`es first so the idle reaper cannot race the agent about to connect) and answers `mcp_endpoint` (the `/browser-mcp` URL, which its description leads with, plus `mcp_available`/`mcp_reason`)/`ws_endpoint`/`http_endpoint`/`pages`/`note`, refusing a caller whose reach excludes `local`. The go-sdk hands a tool the request's headers but not its `Host`, so `withRequestBase` stamps `X-Lasso-Request-Base` onto every `/mcp` request — **`Set`, not `Add`**, so a client cannot supply its own and steer where an agent is told to connect. The description carries the etiquette (open your own tab, don't navigate or close others', close yours, `localhost` is lasso's machine) because it is what the model reads.

### Profiles (`src/browserprofiles.go`, `src/mcp_browser_profiles.go`)

A profile is a named shared browser with its own persistent cookies/logins and its own proxy. The human picks one at the bottom of the Browser tab (Agent mode); agents manage them over `/mcp`.

- **A profile is its own Chromium PROCESS, not a browser context.** Chromium reads `--proxy-server` once per process, and `Target.createBrowserContext`'s per-context `proxyServer` only exists for incognito-like contexts whose cookies, localStorage and IndexedDB die with them — exactly what a profile must not do. A user-data-dir per profile is the one thing that persists all of it. Everything above (lazy start, idle stop, the systemd cap, the pid-file reclaim, `Default/Sessions` deletion, relaunch-on-proxy-change) is per `browserManager`, and there is one manager per profile that has been used. The cost: each RUNNING profile is a Chromium under its own cap (`-browser-cpu` each, not shared); an unused one costs nothing, and each idle-stops on its own. `browserFleet.run` is the one ticker that reaps them all.
- **The default profile is the one lasso always had, unchanged**: `<lassoDir>/browser-profile`, its proxy in `settings.browser_proxy` (so an older lasso on the same db keeps working), bare `/cdp` and `/browser-mcp`, `sharedBrowser`. Other profiles are one JSON list in `settings.browser_profiles` (`id`, `name`, `proxy`, `created_at`), with their directories at `<lassoDir>/browser-profiles/<id>`; the default's display name, if renamed, is `settings.browser_default_profile_name`. It cannot be deleted.
- **Ids** are `^[a-z0-9][a-z0-9-]{0,31}$` — a path segment in two URLs and a directory name, so nothing that means anything else in either — derived from the name when not given (made unique with `-2`…), and unique names are enforced case-insensitively. Anything that takes a profile (the tools, `POST /api/browser`) accepts an id or a display name (`resolveProfile`). At most 32 profiles.
- **Addresses**: `/cdp/p/<id>` (browser target), `/cdp/p/<id>/devtools/…`, `/cdp/p/<id>/json/…`, with `/json` websocket URLs rewritten back through the same prefix (`rewriteCDPJSONAt`) — a rewrite to bare `/cdp` would silently hand a client the default profile's browser. `serveCDPRouted` runs the Origin guard before it looks the profile up. `/browser-mcp/<id>` gives a session whose child dials `/cdp/p/<id>`; an unknown profile is 404 before anything spawns. A profile's stop closes only ITS sessions (`browserStoppedFor`); the cap on children stays global.
- **Delete** retires the manager first (`retired`: a request still holding it cannot relaunch into the directory), stops it, drops it from the list, then removes the directory — every login in it. A new profile that reuses a deleted id starts with its directory wiped, so it never inherits a predecessor's logins.
- **HTTP**: `GET /api/browser` keeps its top-level fields as the default profile's and adds `profiles` (each: `id name proxy default running started_at capped reason note pages ws_path mcp_path`). `POST /api/browser {action, profile?}`, `POST /api/browser/proxy {proxy, profile?}`, `GET|POST /api/browser/profiles`, `GET|PATCH|DELETE /api/browser/profiles/<id>` (400 plain text for input, 404 unknown, 502 = stored but the relaunch failed). Ordinary UI routes behind UI_AUTH. Every change broadcasts a `browser-profiles` SSE event so other lasso tabs refetch the list.
- **MCP tools**: `list_browser_profiles`, `create_browser_profile`, `update_browser_profile`, `delete_browser_profile`, `list_browser_tabs`, `open_browser_tab`, `show_browser_tab`, `close_browser_tab`, and `shared_browser` takes `profile`. All refuse a caller whose reach excludes `local`. They manage WHICH pages exist and which one the human sees; driving a page stays `/browser-mcp/<id>`'s job. Tabs are opened with `PUT /json/new` and closed with `/json/close/<id>`, ids checked against `^[A-Za-z0-9_-]{1,64}$` before they go into a path. `open_browser_tab` accepts only http(s) and `about:blank` (a bare host gets `https://`, `http://` for loopback) — `file:`/`chrome:`/`javascript:` are not pages to show a human.
- **`browser-open` is `open_file` for tabs.** `open_browser_tab` (unless `show:false`) and `show_browser_tab` push `{profile, tab_id, url, from}` to every connected tab, and report `delivered` honestly (0 = nobody saw it; the tab is still open in the browser). Only a VISIBLE lasso tab acts: it reveals the Browser tab, forces Agent mode for that client without rewriting `ui_state.browser_mode`, switches to the profile, and selects the tab once discovery reports it (a wanted-but-not-yet-discovered target must not be clobbered by the fall-back-to-the-first-page rule).

### The browser MCP endpoint (`src/browsermcp.go`)

`/browser-mcp` serves Google's chrome-devtools-mcp to agents at ONE streamable-HTTP MCP URL, already pointed at the shared browser: `claude mcp add --transport http lasso-browser <lasso>/browser-mcp`, nothing installed on the agent's machine, lasso's auth in front. `GET /api/browser` reports `mcp_available`/`mcp_binary`/`mcp_reason`/`mcp_sessions`; Settings shows the URL, the add command and the live count.

- **Why a bridge.** chrome-devtools-mcp is stdio-only — no HTTP server mode — so lasso runs it as a child and speaks MCP on both sides with the go-sdk already in `go.mod` (`mcp.CommandTransport` + `mcp.NewClient` to the child, `mcp.NewStreamableHTTPHandler` to the agent). Each child tool is mirrored with the low-level `Server.AddTool` and its handler forwards name + raw arguments and returns the child's `*CallToolResult` untouched, so image content (screenshots), `structuredContent`, `isError` and `_meta` pass through as chrome-devtools-mcp produced them. Pagination of the child's `tools/list` is followed. A tool whose input schema is not an object is skipped with a log line rather than handed to `AddTool`, which panics on one.
- **One child per MCP SESSION, not one shared child.** chrome-devtools-mcp keeps per-client state — the selected page its page-scoped tools act on, console/network buffers, emulation — so two agents behind one child would steer each other's page. `getServer` returns a fresh `*mcp.Server` per session-less request (in practice, per initialize; anything else without a session id fails initialization and the SDK closes it), and a receiving middleware on `initialize` spawns the child and registers its tools BEFORE the initialize result is built, so the capabilities and the first `tools/list` are the child's. A spawn failure is the initialize's JSON-RPC error — binary missing, `exited during startup (exit status N)` with the tail of its stderr, or a handshake timeout — and the SDK drops the half-open session. The server declares `tools` with `listChanged:false` up front, or `AddTool` would queue a `tools/list_changed` at a session that has not had its initialize answer yet.
- **The cap** (`-browser-mcp-max`/`LASSO_BROWSER_MCP_MAX`, default 8) counts live children plus initializes still spawning (a reserved slot), so a burst cannot overshoot; over it the initialize fails naming the knob.
- **Lifecycle — every end kills the child.** A session ends on DELETE, on `SessionTimeout` (30m with no request; the SDK pauses it while a POST is in flight), when its child dies (a watcher on `ClientSession.Wait` closes the server session, so the client re-initializes rather than calling tools on a corpse), and at shutdown (closed right after `draining`, before `srv.Shutdown`, so an agent's open stream does not hold the drain). Closing the child is the SDK's stdio close (stdin, then SIGTERM, then SIGKILL, `browserMCPTerminate` apart) followed by a SIGKILL to its process group (`Setpgid`, plus `Pdeathsig` on linux like Chromium's) and a `Wait` when the SDK's close did not reap it — `Client.Connect` returns an unsupported-version failure without closing its transport.
- **The shared browser stopping closes every session** (`browserManager.onStop` → `browserStopped`): a stop, an idle stop, the stop half of a relaunch (proxy change, restart), and a crash. The children's CDP connections belong to the process that just ended, and a closed session makes a spec-compliant client re-initialize (the old id answers 404) onto a fresh child and the new browser. The set is snapshotted synchronously in the hook — a session opened after this moment is on the next browser and must survive — and closed in the background, because the hook runs with the launch semaphore held. Child first, then `ServerSession.Close`, which waits for in-flight calls that only return once the child is gone. Idle stop rarely fires under a session anyway: a child that has connected holds a `/cdp` websocket, and that is an in-flight request.
- **It dials lasso's OWN `/cdp`, never Chromium's port.** `/cdp` is stable across relaunches, starts the browser lazily, and its in-flight counter is what keeps the idle stop off while an agent is connected. The address is the one the main listener actually bound (`setListenAddr` after `listenWithFallback`; an unspecified bind is dialed on 127.0.0.1), `ws://` since it is lasso's own listener.
- **The internal token** (`internalCDPToken`, cdpproxy.go): 32 bytes from `crypto/rand` per process, memory only, never logged, handed to the child as `--wsHeaders '{"X-Lasso-Internal":…}'` and stripped before the proxy talks to Chromium. The agent's credential stops at `/browser-mcp`; the child is lasso's own process and has nothing else to present. `withInternalCDP` wraps the OUTERMOST handler, not `withCDPAuth`, because with `-require-access-header` a loopback dial from the child carries no Cloudflare identity and the Access gate would refuse it before `withCDPAuth` ran; it matches `/cdp` paths only (constant-time), so the token opens nothing else, and `serveCDP` still applies the Origin guard. It rides argv because chrome-devtools-mcp reads websocket headers from nowhere else; argv is world-readable on the box — measured, briefly: the child sets `process.title`, after which `/proc/<pid>/cmdline` reads just `chrome-devtools-mcp` — which is no worse than a loopback lasso's open `/cdp` to the same users.
- **The child's flags are lasso's** (`browserMCPArgs`, then whitespace-split `LASSO_BROWSER_MCP_ARGS`, a later duplicate winning in yargs): `--wsEndpoint`/`--wsHeaders` above; `--no-usage-statistics --no-performance-crux` (the URLs an agent visits are nobody's telemetry); `--screenshotFormat jpeg --screenshotQuality 80 --screenshotMaxWidth 1280 --screenshotMaxHeight 1280`, because the browser renders at `-browser-scale` 2 and an unbounded PNG costs an agent ~4x the image tokens (measured through the bridge: example.com comes back 1280x713 JPEG, ~17 KB). chrome-devtools-mcp ≥1.10 defaults to `--pageIdRouting`, so page-scoped tools (e.g. `take_screenshot`) want a `pageId` from `list_pages`/`new_page`; lasso leaves that default alone.
- **Its environment is an allowlist** (`browserMCPEnv`): PATH, HOME, locale, TMPDIR, XDG dirs, mise's directory settings (mise's shims need them to find node; `MISE_GITHUB_TOKEN` is a `MISE_` var too, hence directories only), plus `CHROME_DEVTOOLS_MCP_NO_USAGE_STATISTICS=1`. Never lasso's `UI_AUTH`/`MCP_OAUTH`/`LASSO_MCP_TOKEN`, nor anything else the operator's shell exported: this is a process driving arbitrary web pages. Its stderr goes to lasso's log as `browser-mcp[<pid>]:`, at most 30 lines a minute per child, with the tail kept for a startup failure.
- **No `npx` fallback, on purpose.** The binary is `-browser-mcp`/`LASSO_BROWSER_MCP` (a path or PATH name; `off` → the endpoint answers 503 with the reason) or `chrome-devtools-mcp` on PATH. Fetching an unpinned package from the registry at runtime, on the machine holding the browser's logged-in profile, is a supply-chain hole; the docs tell the operator to `npm i -g chrome-devtools-mcp` or `mise use -g npm:chrome-devtools-mcp`. Not installed → a NEW session gets 503 with that hint (a request naming an existing session still reaches the SDK, so it can be closed).
- **Per profile**: `/browser-mcp` drives the default profile and `/browser-mcp/<id>` another (see Profiles); the session remembers its profile and adds a line to its instructions naming it.
- **Mounted at `/browser-mcp`, not under `/mcp/`** — that prefix is lasso's own MCP server's. `DisableLocalhostProtection` for the same tunnel-Host reason as `/mcp`.
- **Tests fake the child without node**: `TestMain` re-execs the test binary as a stdio MCP server when `LASSO_TEST_FAKE_BROWSER_MCP` is set (`browsermcp_test.go`), passed through the bridge's `ExtraEnv` seam since the child's environment is otherwise an allowlist.

### Terminal links

**Terminal links open in the Browser tab by default** (`lib/sidebar-browser.ts`, `wireLinkOpen` in `lib/terminal.ts`; Settings → General, `ui_state.terminal_links_in_sidebar`). xterm opens both a detected URL and an OSC 8 hyperlink as `window.open()` with no URL, then `location.href = url`, so the terminal document's `open` returns a stand-in whose href setter routes the link. Cmd/Ctrl-click keeps a new tab.

- **Routing depends on the mode actually SHOWN**, which `BrowserTab` publishes (`setEffectiveBrowserMode`) — not the stored preference, which says `live` on a lasso with no Chromium. It starts as `embed`, so a link clicked before the tab ever rendered gets the conservative routing. In Embed an `http://` link on an https lasso still goes to a new tab (mixed content would only show an error); Live is exempt, since Chromium is not subject to this page's mixed-content rules.
- **In Live a link loads into the page on screen** (`Page.navigate`; with no page yet, `navigate` opens one). One page at a time is the point: a link stacking up an invisible page per click would be pages nobody can see. `BrowserTab` holds the request (`OpenRequest`) until whichever mode ends up on screen takes it, because a link clicked before `/api/browser` answers is aimed at Live and must still land if the answer is "no Chromium"; Live parks it (`pendingOpen`) until its socket is up.
