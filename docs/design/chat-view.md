# Chat view (`src/chatview.go`, `src/web/src/components/ChatView.tsx`, `src/web/src/components/AgentSidebar.tsx`, `src/web/src/components/AgentsTab.tsx`, `src/web/src/components/AgentParts.tsx`, `src/web/src/components/NewDialog.tsx`, `src/web/src/lib/agents.ts`)

The terminal column's other half: herdr's focused pane rendered as a conversation, so a session is readable and answerable from a phone. It is an **overlay** over the terminal iframe, which stays mounted and sized underneath — a swap would refit the shared pty to nothing and reflow every other pane. That is also what makes it the phone's way to type: the input dial lives inside that iframe, so the overlay puts it out of reach, and the footer toggle that opens the chat is `md+` only — below `md`, phone or desktop window dragged narrow, the way in is the chat button the dial carries above its root (`.dial-chat`, a dedicated control rather than an arc target: entering the conversation is a destination, not one of the terminal's input controls, and 44px against the root's 58 so it does not read as a second dial; `.dial-sidebar` is its mirror below the root). Read-only over `/api/chat`; the composer posts to `/api/chat/send`, which types into the pane the transcript belongs to.

Rows come from the agent's **transcript file**, never from the PTY — a file the agent appends to, so nothing pushes it and the view polls (2s, paused in a hidden tab), paging backwards by byte offset. Resolution starts at the TAB's host (`reqHostBackend`) and follows the same two hops the file viewer does (`chatScreenPane`, below), deliberately NOT `cwd_host`: the chat is about the pane herdr itself is DRAWING, while `cwd_host` is where that pane's *files* live.

- **The pane on screen is not always the tab host's** (`chatScreenPane`). A chat resolved against `reqHostBackend` alone is right for an ordinary pane and wrong for both of the ways another machine ends up on screen — the same two `activeCwd` already resolves. A **machine** selected in the terminal's own herdr client (`clientMachineHop`) draws another server's whole session, so the local herdr's focused pane is not even visible: the chat showed a stranger's conversation and the composer typed into a pane nobody could see. An ssh **attach** (`paneSSHHop`) puts a remote pane inside a local one, so herdr names a session whose log is on the far host: every such pane read "This session's transcript is not on this host yet." about a file that was never coming. Both now resolve through `hopPane` — the far side's backend plus its pane — and `serveChat` rebinds `be` to it, so the pane listing, the agent records, the stat and every byte of the transcript come from one host. The payload's `host` is that host, which is what makes the composer, the ask answerer, the pane close and a relative image path in the prose all address the machine the agent is actually on.
- **A pane id is never carried across a hop.** herdr's ids are unique only within one server (`wQR:p1` exists on every machine that has been up a while), so looking the browser's local id up in a remote listing is a coin flip between the right pane and a stranger's. The far side is addressed the way the hop names it: the attached agent, or that server's own focused pane.
- **The two hops degrade differently, and deliberately.** An unreadable MACHINE is a note (`Can't read <host>'s session.`) rather than a fall back to the tab's own focused pane — that pane is not what the terminal is drawing, so falling back is the bug, not a safe degradation, and the composer is dropped with it. An unreadable ATTACH keeps the local pane, because the local pane IS the window the reader is looking at and typing into it still reaches the far side over ssh.
- **herdr reports a session two ways, and only one of them is a path.** omp gives `kind=path` — an absolute `.jsonl`, used as-is. Claude Code gives `kind=id`, and that is the whole reason this needed its own resolution: the id is looked up at `~/.claude/projects/<slug>/<id>.jsonl` on the pane's own host, `slug` being the pane's cwd with every non-alphanumeric character turned into `-` (claude's own scheme), a scan of the project directories as the fallback when the cwd cannot be guessed. So a claude pane reads its log over SFTP on a remote box exactly as an omp one does. Before this, every claude pane answered "no session" while its transcript sat on disk.
- **A session lasso cannot resolve gets a note, not silence**, and a value that is not an absolute `.jsonl` is refused outright — it reaches a filesystem read on a machine lasso may not be browsing. **An empty view is either a WAIT or a verdict, and the payload says which** (`starting`). A newly created agent spends its first seconds with no session for herdr to report — the CLI is still starting in the pane — and then with a session whose log is not on disk yet, and both read as "No agent session in this pane." about an agent the reader had just asked lasso to create. `paneBooting` claims the session-less pane, and it can only do that from lasso's OWN record (herdr reports an agent in the pane either way; the records come in as an argument so the rule is testable without a db); the log-not-written case needs no record at all, since herdr named a transcript and that transcript is coming. The view shows the orb for anything flagged `starting` and a plain sentence otherwise — so a pane lasso never created, and one whose boot finished long ago (`chatBootGrace`), keep the note that promises nothing.
- **Claude's log is not omp's, and `parseClaudeTranscript` is where the difference lives.** The record TYPE is the role, and a plain user turn's content is a bare string rather than a block list; a tool result is a block on a USER record instead of a message of its own, so it is paired by `tool_use_id` and buffered when the call it answers sits in an older page (the same forward-result window omp needs, in claude's shape); `usage` sums input plus both cache directions; the title is the session's own `ai-title`; `stop_reason` is what decides "working".
- **Codex is the third shape, and its log cannot be read through the window** (`src/codexchat.go`, `src/transcriptlog.go`). herdr reports it `kind=id`; the id is a UUIDv7, so its timestamp names the `~/.codex/sessions/YYYY/MM/DD/` directory (host-local date, so the UTC day and both neighbours are tried) and nothing is walked. The conversation is the `response_item` records; turn state is `event_msg` (`task_started`/`task_complete`/`turn_aborted`, the last also settling any card it left running); the user role also carries what Codex injects (`<environment_context>`, AGENTS.md, the `<image>` tags around a paste), which is filtered. Tools mostly run as a JavaScript `exec` cell, so a card takes its title from the first `tools.X(` it calls and its subject from that call's `cmd:`/`path:`/`prompt:` literal. **Images are inlined as base64, so one record runs to tens of megabytes** (44 MB lines in a 408 MB log): the shared `chatReadBytes` tail would land inside one and page no further. So the log is read line by line through `elider` (every string past 64 KB cut to a prefix, a data URL to its scheme) with the line boundaries cached per file — the log is append-only, so each giant line is read once per process rather than per 2s poll, which over SFTP is the whole difference. **This is not Codex-only any more: every harness pages through it** (`readLogPage`). claude and omp inline a *pasted* screenshot as base64 in the user record just the same (a 52 MB claude log had fifty records past 256 KB, the largest 1.3 MB), and the old raw byte window landing inside one parsed to an empty page that reported offset 0, i.e. "top of the conversation" one page up. A request scans at most `logScanMax` (64 MB) and a page it cut short with no rows still reports its lines' offset, so paging never mistakes an image-only stretch for the top. **Sending needs the ANSI screen**: Codex's empty composer shows a placeholder, told apart from a draft only by being dim, so `paneComposerState` reads `format=ansi` for codex (`detectCodexComposer`). **Claude needs it too**: an idle Claude Code composer shows a dim suggested next prompt (`❯ commit it`), which plain text reads as a draft, so every chat send to an idle pane was refused. Claude's screen goes through `undimmed` (dim cells blanked) before `detectClaudeComposer`.
- **Subagent traffic is a different conversation, and claude shares the file with it.** Its records are flagged `isSidechain` inside the parent's log (and also written to `<session>/subagents/*.jsonl` beside it, which are entirely sidechain and so parse to nothing), so the parent's view shows the Task card and its result rather than a subagent's reasoning spliced into the middle of it.
- **A turn that was only a pasted screenshot says so.** It carries no text, so without a row the conversation reads as if that message — and the answer to it — came from nowhere.
- **The composer is three-valued on purpose** (`confirmed`/`refused`/`uncertain`). A composer that clears its draft on "uncertain" loses a message; one that retries can duplicate a turn that did land. Neither is a call the server can make for the human. **⌘Enter sends and a bare Enter breaks the line** — it was the other way round, which made every paragraph break a sent message in a field whose whole purpose is prompts written as paragraphs; with the break on Enter, Shift+Enter breaks it too, so a terminal user's habit still works. The button stays the phone's submit, since a software keyboard has no ⌘.
- **The chat's left sidebar lists the FLEET's agents, and the footer's left-hand toggle opens it** (`AgentSidebar.tsx`). That one button means two different things, because the two views have two different left sidebars: in the TERMINAL it sends herdr its own `toggle_sidebar` chord (`lib/terminal.ts:toggleHerdrSidebar` — the default `prefix+b`, since herdr's socket API has no method that opens or closes its sidebar and reports no state for it either, which is why the button is an action there and never an indicator), and in the CHAT it toggles lasso's own panel with a real `aria-pressed`. The panel shows agents ONLY — a pane with no agent is a shell, and the chat cannot display one — one row per conversation **across every connected machine**, this tab's own host first and the rest in name order. That machine is a chip on every row rather than a field of the truncated line, because with the fleet in one list it is what tells two same-named agents apart; next to it sit the harness and the worktree, and above them the name (workspace → pane label → tab → terminal title, herdr's own precedence) with the status, which gets a word for the two states a human acts on (`working`, `blocked`) and a plain dot for the rest. Everything about a row is shared by both surfaces — `AgentLines`/`AgentStatus` in `AgentParts.tsx`, the list and its naming in `lib/agents.ts` — and a row's identity is HOST + pane id (`paneKey`), since herdr's ids are unique only within a host.
- **Below `md` that list is a SIDEBAR TAB instead of a column** (`AgentsTab.tsx`), first in the right panel's own tab strip. It was a sheet inside the chat, reachable only from the chat and only by a glyph in its header; it is in the sidebar now because the sidebar IS a phone's chrome — the same panel carries Files, Settings and (in its header) the creator, the strip already remembers which face you were on, and from there the list is reachable from the TERMINAL too, which a sheet inside the chat never was. One column on a phone, two as soon as they fit (`sm:grid-cols-2`), since a tile holds a name, a machine, a worktree and a status and none of those grow with the viewport. Both surfaces render one list from **`lib/agents.ts`** (`useAgents` + `agentName`/`agentSub`, with the marks in `AgentParts.tsx`): they must agree on the naming, the status vocabulary and the address, and they are never both on screen — the column is `max-md:hidden` and the tab is `md:hidden`, so exactly one is reachable at any width. **A tab that hides itself needs a fallback**: a window widened across `md` while Agents is selected would leave a pane showing under a strip with nothing lit, so `App.tsx` watches `(min-width: 768px)` and drops `rightView` back to Files. A pick focuses the agent, **closes the panel** — below `md` it covers the very view that answers the tap — and lands on that agent's **conversation, never the terminal** (`App.tsx:pickAgent`): the list is one row per conversation, so a pick is a request to read one, and a phone dropped on the terminal instead would answer it with a pane you can neither scroll back through nor type into without the dial. The keyboard is deliberately not handed to the terminal on the way (the panel's own close does that), since focusing xterm would pop a phone's keyboard over a session nobody asked to type into and aim it at herdr rather than at the composer.
- **Ending a pane belongs to the ROW, not to the panel** (`AgentsTab.tsx`'s `Tile`). It was a ✕ in the tab strip beside the panel's own close, which is two crosses a thumb apart where one shuts a panel and the other kills a session. On the row it addresses something on screen and names it in the question (the same `AlertDialog` the chat's md+ glyph raises). It is a SIBLING of the selecting button, not a child — a button inside a button is invalid, and a tap meaning "end this" must not travel through a handler meaning "read this" — so the hover fill sits on the wrapper and the tile lights as one thing under either half. `closeAgent` lives in `lib/agents.ts` beside `focusAgent`, for the same reason: the address is the row's (host + pane id, unique only together) and the list that must forget the row is that hook's. It drops the whole `all-panes` cache (`qk.allPanesAny`) rather than waiting, since `panes_rev` only carries a close on the tab's OWN host.
- **The panel's close is `PanelRightClose`, the mirror of the chat header's `PanelRightOpen`** — not a bare ✕. Beside a row's close-pane glyph a plain cross reads as the same kind of thing; the paired panel glyphs are what say which one ends a session. **New agent** stays in the strip's `trailing` and only while Agents is selected: it makes an agent, which is what the tab lists. It is the footer's own `openNew`, and `agentsOnly` counts this tab, because below `md` — the only width it exists at — it is the only New on screen.
- **The chat header is the whole chrome below `md`, and it carries the creator.** The title takes the left edge — and it is herdr's **workspace label**, the name lasso's auto-titler wrote from the agent's prompt and the same one the agent panel lists it under; the fallbacks are the harness's own session title and then the pane's own title (`workspaceLabel` in main.go; `~` does not count, being herdr's placeholder for a workspace it was never given a name for, which is a cwd rather than a name — note the pane title is seeded first and the session title overrides it, so the effective order is label → session title → pane title). A fresh agent with no label and no session title shows the slug that every surface used to — the unique identifier this ordering exists to keep out of a header. The right holds two glyphs below `md` — Terminal, then Sidebar on the outer edge, where the panel it opens comes from and where the footer keeps its own sidebar control at md+ — and at md+ just the close, since the footer already carries Agents (its left-hand toggle), Sidebar, Terminal and New while nothing anywhere closed a pane, and the chat is where you are looking at the pane in question. Those two were a menu titled "Chat actions" carrying five items; three of them moved into the sidebar panel (the agent list is a tab there, New agent and Close pane are its header's), which leaves exactly the two that are about this VIEW rather than about an agent — and two icons fit a phone's title row where four did not, with a destination one tap away beating a named item two taps in. **Sidebar is an OPEN, not a toggle** (`App.tsx:openSidebar`): below `md` that panel overlays the whole screen, so this header only exists while it is collapsed, and until this button there was no route to it from the chat at all on a phone — the footer is `md+` and the dial's own sidebar button lives inside the terminal iframe the chat covers. It stamps `markSidebarIntent` like ⌘\ does, being a human moving the synced layout. Its return path is the panel's own ✕ (`closeSidebar`), which hands the keyboard back to the terminal **only when the terminal is what it uncovers** — over the chat the iframe is hidden, so focusing it would pop a phone's keyboard for a surface nobody can see and aim the next keystrokes at herdr instead of the composer. **Closing asks first** (`AlertDialog`): it is herdr's own `pane.close`, which is what ends the agent in that pane — there is no softer "detach" — so it is confirmed rather than done. Below `md` the same question is asked from the sidebar's Agents tab, which is where the close lives at that width. lasso navigates nothing afterwards: the chat follows herdr's focused pane, so the view has already moved on by the time the pane is gone. The creator reached from a reading view is `agentsOnly` (`NewDialog`): no mode tabs, title "New agent", because the chat reads an agent's session and a bare shell has none to show. A created agent is focused like any other (`focusCreatedAgent`), which is what puts its conversation on screen with no view change — the create path writes `leftView` nowhere.
- **Dismissing the creator from the chat does not hand the keyboard to the terminal** (`NewDialog`'s `onCloseAutoFocus`, on `agentsOnly`): focusing that hidden iframe pops a phone's keyboard over the view the user just returned to, and aims a desktop's next keystrokes at a terminal nobody is looking at — the same reason entering the chat blurs it. It drops focus instead, so the composer takes it on the next tap, as it does after a pick in the sheet. Everywhere else a dismissal still returns the keyboard to the terminal. **`⌘I` is the one shortcut that leaves chat**: a new terminal is not something the chat's dialog can make, so it hands the screen back to the terminal first and opens the creator there, rather than answering a terminal shortcut with an agent form.
- **⌘K means "which conversation next" in the chat and the agents grid** (`AgentSwitcher.tsx`). In the terminal it is still herdr's own pane search; from a reading view that search is the wrong answer twice over — it knows one machine's panes, and it answers by moving a terminal nobody is looking at. So there it opens a filter-as-you-type list of the same fleet `useAgents` feeds the sidebar (every whitespace term must match the name, harness/worktree or machine), and a pick switches the view to the chat and then focuses the agent, the same order the grid's card open uses. Closing it blurs rather than refocusing the hidden terminal, for NewDialog's `agentsOnly` reason.
- **Selecting an agent moves the TAB when it lives elsewhere, then focuses it** — `moveTabToHost`, then `api.focus` with the row's **`pane_id`** (herdr's `pane.focus` focuses the pane's workspace, its tab and the pane, so a split tab's two agents — two rows here — are individually reachable; `workspace_id`/`tab_id` ride along only as the server's fallback for a pane closed since the listing, and focusing the pane is also what marks it SEEN, clearing a finished agent's Done badge). The order is the whole thing: the focus call is addressed to the host the tab is on, and the chat follows that host's focused pane, so attaching after focusing would land the focus on a machine the chat is not showing. It is the same two steps the creator's success path takes, and the chat then follows the pane over SSE, so the highlight is never a second source of truth: a row is current because herdr says that pane is focused, with the pick standing in until the host feed's event or 2s poll catches up. `panes_rev` covers this tab's host (create/close/rename) and a 5s poll covers the other machines plus the one thing no layout revision carries, an agent's status; a host whose enumeration failed contributes no rows and says so at the end of the list rather than letting its agents look deleted.
- **The panel takes width from the CHAT, not from the terminal** — it is a flex column inside the chat overlay, which already sits over a terminal that stays mounted and sized. A real panel there would refit the shared pty every time someone opened a list, reflowing every other client's herdr for a panel nobody in those panes can see. Per-TAB for that reason (and unlike the right sidebar's synced layout). Below `md` it is not hidden but *replaced*: the footer that opens it does not exist there, so the sheet above is that width's way to the same list.
