# `lasso mcp` — the tool surface as a CLI (`src/mcpcli.go`)

`lasso notify` proved the shape and `lasso mcp` is its general case: every registered MCP tool as a shell command, over the same endpoint, with the same credentials and the same one-shot session (`dialMCP`, shared by both). `lasso mcp` lists, `lasso mcp <tool> -h` shows one tool's flags, `lasso mcp <tool> [flags]` calls it. An agent with lasso's MCP server configured calls the tools directly; one that only has a terminal — which is most of them, most of the time — types this and gets the same behavior from the same descriptions.

- **The flags are built from the schema the SERVER advertises, never from a table in the file.** The binary you type is not necessarily the binary answering (a `lasso update` since the shell started, `LASSO_URL` pointing at another box), and a hand-kept copy of the tool list is precisely the drift notify was written as an MCP client to avoid. A tool added to `mcp_tools.go` is on the CLI the moment the server restarts, with no second place to edit — which is also why `mcpcli_test.go` asserts against the real `/mcp` handler rather than a fixture.
- **An omitted flag is ABSENT from the call, not a zero value.** The tools distinguish the two (an empty `host` means "search every host I may reach", not "the host named empty string"), so `argFlag` records whether it was set at all and only set flags reach `Arguments`. Required fields are checked locally purely to save a round trip — the SDK validates the same schema server-side, so this mirrors its answer rather than inventing a stricter one.
- **Both spellings resolve, for the tool name and every flag.** The model-facing docs say `get_agent`/`agent_id`, every CLI listing says `get-agent`/`--agent-id`, and refusing whichever one someone has in front of them is a papercut with no upside. The kebab alias is registered against the *same* `argFlag`, so it is one field, not two.
- **A blocking tool's own timeout outranks the transport deadline** (`toolSelfTimeout` + `mcpCallSlack`). A tool asked to wait three minutes, cut off at the CLI's two, reported a bare "context deadline exceeded" about a call that was going fine (the tool was `wait_agent`, since removed; the mechanism stays for any tool that takes its own timeout). The root context therefore carries no deadline — the session has to outlive the setup phase — and each phase takes its own child: `-timeout` for dial/list, and for the call whichever is longer of that and the tool's own timeout argument plus slack. The argument is recognized by name and unit suffix rather than a list of tools, so it can only ever *extend*, never shorten.
- **`-json` is accepted after the tool name as well as before**, unless the tool's own schema claims that name. Parsing stops at the tool name (that is what splits our flags from its), so a global would otherwise have to lead — the exact papercut mcp2cli has.
- **A parse error the flag package already printed is not printed twice** (`errFlagReported`): a second copy under a screen of usage reads as two different problems. Explicit `-h` prints to stdout and exits 0, which is what tells it apart from a usage error on stderr exiting 2; only a LEADING help token counts, since a value further along may legitimately be the string `-h`.
- **Structured output is the payload when there is one.** Every lasso tool has a typed `Out`, so the text content beside it is the same data rendered for a model and printing both would double every answer. Indented on a terminal, compact when piped, so `| jq` needs no flag. Exit 1 when the tool itself refused (distinct from a transport failure, which exits 1 through `fatal` and prints no result); exit 2 for a usage error.
- **`notify` and `closeme` keep their own subcommands.** notify's exit code is a contract (non-zero when nothing was listening) and it reads a piped message; closeme resolves `$HERDR_PANE_ID` for you and deliberately POSTs a plain endpoint. Both are the short spelling of a call this can also make the long way.

### `lasso connect` (`src/connect.go`)

Onboarding in one command: registers `lasso` (`<base>/mcp`) and `lasso-browser` (`<base>/browser-mcp`) with every agent CLI on THIS machine. `<base>` is `-url`, else the same `LASSO_URL`/`LASSO_LISTEN` resolution notify and mcp use (`lassoBaseURL`) — the URL this machine reaches lasso on, which on a fleet box is the tunnel/tailnet URL, never 127.0.0.1.

- **Each CLI's own mechanism, read off its `--help`, not assumed.** claude: `claude mcp add --transport http --scope <s>` — it *refuses* an existing name, so an update is `claude mcp remove` + add. codex: `codex mcp add <name> --url` *replaces* in place but drops any `http_headers` while doing it, and has no static-header flag (only `--bearer-token-env-var`, which would make the entry depend on codex's environment) — so headers are written into that table of `config.toml` afterwards by a scoped line edit (`codexSetHTTPHeaders`; go.mod has no TOML library). codex reformats an inline `http_headers = {…}` into a `[mcp_servers.<n>.http_headers]` sub-table on its next write, so the edit handles both. opencode: `opencode mcp add <name> --url --header K=V` replaces, but there is no `remove`, so `-remove` edits `opencode.json(c)` — and refuses a file that only parses with comments stripped rather than drop them. omp: no mcp subcommand; `~/.omp/agent/mcp.json` is edited order-preservingly (`jsonObject`), keeping the human's other keys on the entry. pi: no MCP client by design — skipped with that reason. A new harness in `harness.go` with no `connectTargets` entry fails `TestConnectTargetsCoverEveryHarness`.
- **"unchanged" is read from what the CLI stored** (`~/.claude.json` per scope, `codex mcp get --json`, the config files), never from a memory of lasso's last write, so a hand edit is seen and re-running is always safe. Every file write is atomic with a `.bak` of the file as it was before this run, and strips group/other bits — these files now hold auth headers.
- **The argv/secret tradeoff.** claude and opencode take headers only as argv, so for those two the values are briefly in `/proc/<pid>/cmdline`; codex and omp get theirs straight into their files. It is in `-h`, and every value is masked (`maskSecret`) in anything printed, dry-run included.
- **The probe decides what to register.** `probeLasso` does an MCP initialize with the exact headers it will register, then `shared_browser {start:false}` (so probing never launches Chromium) for `mcp_available`/`mcp_reason`. /mcp unreachable → nothing is registered, exit 1 (`-force` skips the probe). Browser MCP unavailable → `lasso` alone, plus why and the fix. An https base with no `CF-Access-Client-Id` gets the Access service-token hint on failure.
- **Testing it end to end**: run the built binary with `HOME` and `XDG_CONFIG_HOME` pointed at a temp dir (and `CLAUDE_CONFIG_DIR`/`CODEX_HOME` unset) — all four CLIs honor that. Never against a real home.
