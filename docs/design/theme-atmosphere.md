# Theme atmosphere (`src/web/src/index.css`, `src/web/src/lib/theme.ts`, `src/web/src/lib/wallpaper.ts`, `src/web/src/lib/mode.ts`, `src/db.go`, `src/hostpanes.go`)

**Any** theme can wear a **backdrop**, and a backdrop is a real image. Three sources feed one gallery (Settings → Themes): the 27 Retro 82 stills lasso vendors as WebP under `src/web/public/wallpapers/retro-82` (longest edge 1920, plus 320px thumbs; provenance in that directory's `NOTICE.txt`) and describes in `src/web/src/lib/retro82-wallpapers.json`; whatever a theme shipped with, served by the Go side as root-relative `/omarchy/bg/<theme>/<file>` with a 320px `/omarchy/thumb/...` preview beside it (`GET /api/omarchy-themes` → `backgrounds`/`thumbs`, two positionally-parallel arrays zipped by `shippedPairs`); and pictures a human handed lasso by URL or upload. Palette hexes come from `/api/theme`, never from CSS.

- **The two shipped sources are exclusive, not additive.** Where lasso bundles a set (retro-82) it wins outright and the catalog's own images for that name are skipped: upstream's set is the same *pictures* under different filenames, so merging would offer every still twice under two labels and a URL dedupe cannot see it. The bundled copy is also the superset, and the one with real thumbnails.
- **Nothing is authored in CSS but the rules that read two custom properties.** `lib/theme.ts:applyAtmosphere` composes the whole `background-image` stack — scrim over shading over `url(...)` — and pins it as `--atmo-layers`, with the theme's own terminal background as `--atmo-base`, on `<html>`. `index.css` then has one body rule (`:root[data-atmosphere] body`) that paints `var(--atmo-base)` + `var(--atmo-layers)` fixed/cover, and `termAtmosphereCSS` mirrors the same two values into each ttyd document. One composition, two documents. The attribute is matched on **presence** (its value is the theme name, for inspection only) because every theme is now a candidate.
- **A backdrop is an explicit pick, per theme, and it belongs to the SERVER.** It lives in lasso's own `ui_state` blob (`theme_atmosphere`, `custom_backgrounds` in `db.go`) and rides the machinery the sidebar and the usage footer already use: a patch `POST /api/ui-state`, a `ui_state_rev` bump on every save, one React Query cache per tab, `syncUIState` on the bump. So a still picked on a phone paints on the desktop within a beat and with no reload, and a browser that has never been told anything wears what the last human chose. Nothing reaches `config.toml` and nothing is mirrored to another host — this is lasso's UI state, not the shared herdr theme, which is exactly why the browser-local *palette* choice (`lib/mode.ts`) stays in `localStorage` while the backdrop for it does not. Keyed by the theme the BROWSER resolved, so switching palette restores the backdrop each one had. Only retro-82 has a default (`04-dusk-guardian`); every other theme starts flat, since a palette switch must not drop a photograph on you. An unknown stored URL — a still dropped by a later vendoring, a custom picture since forgotten — resolves back to that default instead of pointing the backdrop at a 404. **There is no import from the old `localStorage` keys**: a browser's private copy cannot be told apart from a stale one, and letting one seed the shared state would have the last tab to open decide the fleet's backdrop. Re-pick once; every device follows.
- **Merged per theme AND per field, because this is the first part of `ui_state` two humans edit at once.** A JSON decode over the stored struct merges top-level fields, but a map's named entry is REPLACED wholesale — so `serveUIState` detaches both collections before the decode and rebuilds them (`mergeThemeAtmosphere`, `mergeCustomBackgrounds`). Two levels, two races: a laptop dressing rose-pine must not drop what a phone just picked for retro-82 (entry level), and a nudge of the dimming slider must not drop that theme's picture (field level, which is what the `*float64`/`*bool` pointers are for). Detaching them also keeps the decode from writing through the map `stored` still points at, which would make the no-op check that guards the rev bump compare the merge against itself — a 200 with nothing saved. No layout-style claim is needed: unlike the sidebar, nothing re-persists a backdrop unprompted.
- **Only explicit choices are stored, and nothing paints until they arrive.** An absent entry means the frontend's default, never a value written back — so a tab whose fetch is still in flight cannot persist a default over a choice it has not seen. `lib/wallpaper.ts` reports no image and no shading until `uiStateSettled()` (arrived, or failed — a dead endpoint degrades to the defaults rather than to a terminal that never gets its palette pinned), because the alternative is the default photograph appearing and vanishing on a browser whose owner turned it off.
- **A hand-given picture is remembered globally, not per theme** (newest first, capped at 24 on both sides): a photo you like is a property of your screen, and now of this lasso. A URL is used verbatim; an absolute path is read back through `/api/file?path=…&host=…`; an upload goes through `/api/paste-file` (the endpoint terminal paste/drop already uses) and is then referenced by that same `/api/file` URL — so it survives a reload, where a `blob:` URL would not, without lasso growing an image store. It is written as an OP (`remember_background` / `forget_background`), never as a list: a tab sending the whole gallery out of a copy it fetched minutes ago would resurrect a picture another browser just forgot. Only these can be forgotten; a bundled or shipped one belongs to the theme.
- **The scrim is derived, not authored.** `rgba(<theme background>, alpha)`, with `alpha` the Settings "image dimming" slider — default **0.70**. The reset button beside the slider restores this default; existing saved values remain unchanged until reset. It is the outermost layer of the stack, so it washes the image *and* the shading below it, and it is left out entirely when no image is picked (there is nothing to wash). A palette whose background is not a plain `#rrggbb` yields no scrim rather than a guess.
- **Palette shading is the imageless backdrop** (`getShading`, **on** unless a theme's entry says otherwise): two very low-alpha radial washes of the theme's own `blue`/`magenta` (falling back to `cyan`/`green`), one from the top-left, one from the bottom-right. It is what gives a flat theme depth, and it turns the terminal transparent exactly like an image does.
- **Translucency is always a `background-color` with alpha, never `opacity`.** `opacity` would fade the glyphs with the surface, which is the whole thing being avoided: text stays fully opaque everywhere.
- **A surface that COVERS the backdrop reproduces it instead of going flat** (`index.css`, `.chat-overlay .vsurface`). The chat and its agent column must be opaque — they sit over the terminal, and at `--background`'s 62% herdr's own tab bar and text read straight through the conversation — but flat was the wrong opaque: the shading, or the whole backdrop, stopping dead at the chat's edge made the conversation read as a deader surface than the chrome around it, and the Settings shading and dimming controls visibly reached everything except the place the eye spends its time. So those surfaces paint what the body paints — `--atmo-base` under `--atmo-layers`, fixed and cover so the image lands at the same coordinates and the two meet seamlessly at the panel's edge — which is a painting of the backdrop rather than a window onto it: nothing behind can read through, and everything inside (the `--background` root, the `--card` composer and cards) floats on it exactly as the chrome does. The file viewer and the Files panel's empty state keep the flat fill, being reading surfaces with nothing to be continuous with, and `--popover` is still solid.
- **The terminal's backdrop is CSS, not an xterm color.** `applyTermAtmosphere` injects it into each ttyd document (a parent stylesheet does not cross the iframe boundary — the same reason `applyTermFont` re-declares the `@font-face` there), reading the values off the parent's own custom properties so there is one definition. xterm is handed a fully transparent default background and `allowTransparency: true`, so a cell no program has colored paints nothing. Keeping the scrim in CSS makes the tint identical under all three of ttyd's renderers instead of depending on how each composites a half-transparent theme color; ttyd's own `<body>` is neutralized rather than used for the wash, since a second painted surface over a scrim layer would double the tint. Every URL emitted is root-relative or absolute, which is what makes the same string resolve inside a document served from `/terminal/<slug>/`.
- **`applyAtmosphere` is the single chokepoint, and it repaints in place.** `refreshTheme` calls it (so a reload, a re-theme and an appearance change all land there) and so does `subscribeAtmosphere` — a subscription to the persisted prefs' query cache, which fires for a pick made HERE (the optimistic write) and for one made in another browser (the `ui_state_rev` refetch) alike, so no Settings control has to remember to repaint. It compares only the atmosphere slice of `ui_state`, since the same cache entry carries `sidebar_pct`, which a drag rewrites dozens of times a second. `applyTermAtmosphere` **updates** an already-injected stylesheet whose text differs rather than skipping on its presence, and writes nothing when it doesn't, so a pick repaints the chrome *and* every already-loaded terminal iframe with no remount and the reconcile stays free. Before the first palette has resolved it does nothing at all: a pick made while `/api/theme` is in flight is already persisted, and painting a black canvas meanwhile would be a flash of a theme nobody chose.
- **`allowTransparency` is what makes glyphs work.** Without it xterm bakes the background behind each glyph into its texture atlas and every cell becomes an opaque tile. It is pinned in `applyTermTheme` — the one place boot, a re-theme and the post-reconnect reconcile all funnel through — and xterm rebuilds the atlas on the change (the docs' "must be set before `open()`" is stale for 5.3; verified against a live webgl renderer). Writing an unchanged boolean is a no-op in xterm's option setter, so a flat theme pays nothing.
- **The palette and that boolean are one pin, and both halves read the LIVE cache.** `applyTermTheme` takes no theme argument and each retry re-reads `lastXtermTheme`: a snapshot captured before a `setTimeout` outlives the palette it came from, so switching a backdrop theme → a flat one while an iframe is still connecting would land the queued palette — background transparent — under the flat theme's `atmosphereOn=false` pin a quarter second later, i.e. blank tiles until the next reconcile. `reconcileTermTheme` compares `allowTransparency` alongside the background for the same reason: either can drift alone, and half a pin is a broken terminal rather than a mismatched one.
- **The transparent background still has to spell out the theme's own background** (`<theme bg>00`, e.g. `#00172e00` under Retro 82), and that is what makes the backdrop visible *inside herdr's panes* rather than only at its edges: xterm answers OSC 11 with the alpha dropped, herdr records that as the host terminal's background, and its pane renderer emits **no** explicit background for a cell whose default matches the host's (`ghostty_default_bg` → `None` → `Color::Reset`). A different RGB would make herdr paint every pane cell explicitly and the backdrop would never show. It is also the reply omp and opencode read to infer light vs dark, so it must keep the theme's own lightness. A palette whose background is not a plain `#rrggbb` gets no transparency at all — a normally painted terminal, not a broken one.
- **What stays opaque is opaque, by definition.** A cell carrying its own SGR background cannot be made translucent from the outside: herdr's tab bar, status/overlay bars, dialogs and active-row highlights all paint `panel_bg` (the theme's own panel color, so they read as calm flat bands rather than a clash), and so does any TUI that colors its own canvas. herdr's desktop sidebar is `sidebar_bg = Color::Reset` in every built-in theme — deliberately left unset by the override block lasso writes — so it shows the backdrop, and so do a pane's own default cells (`mode=0`, no bg). Worth knowing when checking this by hand: a full-screen herdr overlay (onboarding, settings) paints `panel_bg` edge to edge, so with one open the whole terminal reads opaque and the backdrop looks broken — close them before concluding anything about transparency.
- **A standalone `/terminal/<slug>/` window gets the palette but no backdrop.** The injection is the app page's; nothing else runs in that document. Same class of gap as everything else `lib/theme.ts` reaches in to do.
- **The chrome half is gated twice**: `data-atmosphere` lands on `<html>` only when the effective theme HAS a backdrop AND the chrome is actually following a palette (`chromeFollowsPalette` — appearance mode `herdr`, or a palette named for the scheme in force), since the Nothing light/dark canvases are flat monochrome by design. So a flat-chrome tab still shows the backdrop in its terminals and says so in Settings. Everything keyed off the attribute is additive (body backdrop, translucent `--background`/`--card`/`--sidebar`, the accent hairline on `.term-shell`, which now mixes from the live `--h-*` rather than retro-82's amber and teal), so dropping it restores the chrome exactly — and `--popover` is deliberately never translucent, a menu being a reading surface.

### Appearance and palettes (`lib/mode.ts`, `lib/theme.ts:refreshTheme`, `lib/ui-state.ts`)

What the chrome is painted from is **server state**, not a per-browser choice: `appearance_mode` (`herdr`|`system`|`light`|`dark`, default `system`) plus `palette_light`/`palette_dark` (default `ocai` / `execution-associates`, the brand pair) are three flat fields of `ui_state`, so they ride the patch-merge, the React Query cache and the `ui_state_rev` SSE bump the backdrop and the usage footer already use. Pick Dark on a phone and the desktop repaints within a beat; a fresh browser opens on what the last human chose. Nothing about appearance is in `localStorage` — the keys `lasso-mode`, `lasso-palette-light` and `lasso-palette-dark` are gone and deliberately **not** imported, since adopting one browser's stale choice as the new fleet-wide answer is a worse first impression than the documented default.

The herdr theme itself is a different thing and stays shared *with herdr*: `POST /api/theme-set` writes `[theme].name` in `config.toml`, the TUI reloads, every tab follows the `theme_rev` bump, and lasso mirrors it to the synced hosts and agent CLIs — **while no appearance palette is named**, the one case that refuses the write (`fleetThemeIsPalette`, below). Resolving a palette is therefore a **read** — nothing about a repaint may re-theme the fleet — but an appearance change *made in a browser* pushes the palette it resolved (see "Pushing a resolved palette to the fleet" below), because the agents inside a terminal have to match the terminal.

- **`system` is stored, its ANSWER is per device.** The OS scheme is an observation about the screen in front of someone, not a preference to share, so `resolvedMode` collapses the stored `system` against each browser's own media query. Everything else resolves identically everywhere.
- Outside `herdr` mode lasso may name a theme **per scheme** (`localPaletteName()` collapsing the two fields against `getMode()`/`resolvedMode()`), and `refreshTheme` resolves it through **`GET /api/theme?name=`** — a read: `refreshTheme` writes nothing, whatever called it. That payload paints the chrome *and* the terminals. The defaults only fill a field the stored blob lacks: `saveUIState` writes every field, so an install that has ever saved keeps its mode and palettes, an explicit `""` included. `""` means the flat Nothing chrome and herdr's shared palette in the terminals — the previous behavior, unchanged.
- **One request either way.** `refreshTheme` asks for the named palette when there is one and falls back to plain `/api/theme` if that fails (an uninstalled theme, an older server), so a stale preference degrades to the shared look rather than to no theme.
- **An arriving change repaints through the same chokepoint a local pick does.** `subscribeAppearance` compares only the three-field slice of the cache (plus whether it has settled) and `AppProvider` hangs `refreshTheme` off it — the full repaint: html class, `--h-*` override, every terminal iframe's palette, the backdrop. It is read-only, so a change delivered by SSE cannot echo back out as a write, and nothing remounts. The Settings controls read the same cache (`useUIState()` + `getMode()`/`getPalettePref()`) instead of copying it into React state, which is what used to leave the buttons showing this tab's own choice after another browser changed it.
- **Nothing is readable before first paint any more**, so `index.html` carries `class="dark"` plus a one-line inline script that flips it to `light` when the OS prefers light — the DEFAULT mode's (`system`) scheme, matching `DEFAULTS` in `lib/ui-state.ts` and `getUIState` in `db.go` — and `lib/mode.ts` re-asserts the class the moment `/api/ui-state` lands. A lasso pinned to the other scheme therefore opens wrong for that one round trip. Do not "fix" this with a localStorage mirror: two sources of truth for the same field is the bug this replaced.
- **The OS flip has to re-run `refreshTheme`, not just the class.** `watchSystemMode(onChange)` takes a callback (`AppProvider` passes `refreshTheme`) because the media-query change also changes WHICH palette applies; `lib/mode.ts` cannot import `lib/theme.ts` itself, that being the direction of the existing dependency. `lib/mode.ts` → `lib/ui-state.ts` → `lib/api.ts` is acyclic, which is why the mode can live on server state at all; `AppearanceMode` is declared in `lib/api.ts` (with the payload) and re-exported as `Mode`.
- **The `--h-*` override is written as `:root:root{…}`.** `index.css` declares the light tokens on `:root.light`, which outranks a plain `:root` no matter where it sits in the cascade — invisible while only `herdr` mode (dark class) used the override, and a silently ignored palette the moment a *light* one exists.
- **Each scheme's picker only offers themes of that lightness.** A light palette under the dark class leaves every `dark:` variant in the chrome fighting the palette it sits on, and the html class stays the OS/pinned scheme's.
- **Never send `appearance_mode: ""`.** The server answers 400 and drops the WHOLE patch (see `src/appearance_test.go`); clearing a *palette* is `""`, clearing a mode is not a thing.
- **A theme installed from a URL** (`POST /api/omarchy-themes {url}`) answers with the whole catalog: the Settings pane writes it straight into `qk.themeCatalog`, drops `lib/theme.ts`'s own module-level catalog cache (`invalidateThemeCatalog`) and re-resolves the palette, since an install can hand the theme already on screen a set of images. That cache is deliberately kept for the page's life — including a FAILED fetch, cached as an empty list, so an older server is not asked again on every re-theme. Uninstalling is not offered: the clone is a directory on the machine, and deleting one from a browser is a footgun with no undo.

#### Pushing a resolved palette to the fleet (`lib/mode.ts:pushPaletteToFleet`)

The palette a browser resolves is one value; the theme lasso **writes** — herdr's `config.toml` plus every agent CLI's own theme file (`src/agentsync.go`) — is another, and nothing connected them. So picking a light palette repainted the chrome and the terminals `ayu-light` while omp, opencode, Claude Code and herdr's own tab bar kept whatever the herdr theme picker last set: retro-82 navy panels drawn on a cream canvas. The Settings **"Sync now"** button was the only thing that closed it, by hand.

`pushPaletteToFleet` now makes an appearance change call the same endpoint that button does (`POST /api/theme-sync {palette, quiet}` → `setLocalHerdrTheme` + `syncThemeNow`).

- **Only from the three entry points where THIS device is the cause** — `setMode`, `setPalettePref`, and the `watchSystemMode` OS flip. Never from `refreshTheme`, which also runs for a change that *arrived* over `ui_state_rev`: a push bumps `theme_rev` and repaints every other browser, so pushing from a repaint would have two devices resolving `system` differently re-theme each other forever. The last human to act decides — which is what asking the fleet to follow your screen means, and it is the same `user_intent` distinction `uilock.go` draws for the sidebar.
- **`""` is skipped.** That is `herdr` mode, whose whole meaning is that the fleet's own theme wins; pushing it would be a fleet-wide SFTP write of what is already there.
- **Debounced 500ms, with one retry at 3s.** The controls are clicked in runs (mode, then the palette for it) and the server refuses a second fanout while one is in flight (`themeSyncRunning`, 409). A dropped push is **not** self-healing: `convergeThemeOnProbe` catches a host up against the theme lasso last *wrote*, and a push that never landed never became that. After the retry the remembered palette is cleared so the next appearance action tries again instead of reading as already pushed.
- **`quiet` drops the SUCCESS notice only.** A "synced to 14 hosts" toast arriving fleet-wide seconds after every appearance click is noise; a host that *refused* the write is the one thing a human has to be told, and nothing else would tell them.
- **A palette in force takes the herdr picker off the table.** Both are the same single value, so while one is named `POST /api/theme-set` answers 409 and the Settings select is held with a line saying why (`lib/mode.ts:fleetThemeIsPalette` mirrors the server's `fleetThemeIsPalette`). A pick there would fan the theme no screen is showing out over the palette every screen is, and leave it there: the fan-out and the per-probe convergence both read what lasso wrote to herdr's `config.toml`, so herdr's config has to keep holding the palette for the fleet to stay on it. `herdr` mode — whose whole meaning is that the fleet's own theme wins — keeps the picker authoritative whatever palettes are stored; a pinned mode answers for its own scheme only (a light palette under pinned dark governs nothing); `system` counts a palette named for either, since the server cannot see which scheme a device resolved. Clearing the palette hands the fleet back to the picker, and `pushPaletteToFleet`'s `""` branch forgets what it pushed so the picker's next move is not read as already synced.
- **An edit lasso did not make is not adopted either.** The hub poll (`hub.refreshTheme`) re-resolves `config.toml` every `-poll` (2s) and, while a palette governs, refuses a theme lasso did not write: `herdr`'s own theme popup and a hand edit are seen, logged once per value (`theme: herdr's config.toml names "x", which lasso did not write; an appearance palette governs, so the fleet stays on y`), and dropped. It has to be "not adopted" rather than "adopted but not fanned out": `convergeThemeOnProbe` pushes the HUB's theme to every host that is behind, so adopting the edit would put the fleet on it within a probe sweep whatever the fan-out does — keeping the hub on the palette is what keeps the fan-out, the convergence and every browser that follows herdr on it. Lasso's own writes are still adopted, told apart by the shared record of what lasso last wrote to the local machine (`theme_written:local`, which `setLocalHerdrTheme` marks *before* it writes the file — the fan-out that would otherwise mark it has not run yet, and another lasso may read the file the instant it lands). A stray edit that predates the boot is no longer adopted either: `bootTheme` applies the same rule from the same record (below).

#### Every lasso on one lasso.db is one writer (`agentsync.go`: `themeRecordFor`, `claimThemeConverge`, `lassoOwnsConfigTheme`, `bootTheme`)

A production lasso and a `mise run dev` one share `~/.lasso/lasso.db`, the local herdr `config.toml`, the agent theme files and the ssh fleet. The record of what lasso wrote used to be per-process memory, and on 2026-09-28 that made the two revert each other. A dev booted on `ocai` and converged the fleet onto it. Two seconds later a production tab's appearance push (`POST /api/theme-sync`) had production write `execution-associates`. The dev's poll had no note of that write, so it logged it as a stray edit ("which lasso did not write … stays on ocai"), kept `ocai`, and kept converging it. Dev instances that booted after the write came up on it and did not fight. The rule is the same settings in, the same decisions out, whichever process makes them:

- **The write record is shared.** `markThemeSynced`, `restampLegibility` and `forgetThemeSynced` write through to one `settings` row per host (`theme_written:<host>`: name, backdrop fingerprint, writer instance, build, time). There is one row per host, not one JSON map, so two processes recording two hosts cannot lose an update to a read-modify-write. `themeSynced.by` stays in memory as what *this* process wrote. An unreadable db (closed at shutdown, or locked past busy_timeout) falls back to that memory, the old single-process record. It never reads as "nothing written", because that would re-push every host.
- **Ownership reads it.** While a palette governs, the poll adopts a `config.toml` theme that any lasso wrote (`theme_written:local`), or one that *another* lasso's hub adopted (`theme_hub`, written on every adoption). A process's own adoptions are not counted, which keeps a single lasso's decisions exactly what they were. Every adopting hub fans out. That is redundant across processes, never a revert, since they now agree, and the writers skip unchanged bytes.
- **Boot reads it.** `bootTheme` holds a starting lasso at `theme_hub` when a palette governs and `config.toml` names a theme no lasso wrote or adopted. Before this, a process booting over a stray edit adopted it while the running ones refused it, and the two converged the fleet onto their two themes in turn, every probe, for as long as both ran. With `-theme` pinned, or with nothing recorded, the boot is unchanged.
- **Convergence reads it.** A host whose shared record already matches the live stamp is in step, whoever wrote it, so a fresh process no longer re-pushes the whole fleet. A host another lasso wrote something else to after this one wrote the live theme (a stale push landing late) reads as behind again, and the next probe of any lasso puts it back. A record left by a **different build** is re-verified **once per process**: a new build may generate different bytes for the same theme, and reaching the fleet with them on restart is what `lasso update` relies on. It happens only once so that dev and production, always different builds, cannot re-push each other forever. A restart of the *same* build now trusts the record instead of re-pushing everything.
- **A convergence push re-checks the live theme after it gets its `themeSem` slot.** The slot can take seconds, and a theme that moved meanwhile (here, or in another lasso whose write this hub adopts on its next poll) must not be written after the fresh one. The change's own fan-out and the next probe cover that host.

What stays per-process is deliberate: the in-flight claims, and the browser-side rule that only `setMode`/`setPalettePref`/the OS flip push a palette. Under `system` mode, two devices whose OS schemes differ still hand the fleet back and forth when each one acts. That is the documented "last human to act decides", not a race between processes.

### Legible agent text under a backdrop (`src/legibility.go`, `src/agentsync.go`)

A backdrop changed what a pane's glyphs land on and nothing downstream noticed. The terminal under one is served transparent (`transparentPanelBG`), so an agent's own cells show a photograph washed by the scrim, while omp's and Claude Code's generated themes were still mapped straight off the palette — colours an author chose against a flat canvas. Ayu Light under a wallpaper at 0.75 dimming was the report: omp's inline code (`mdCode` = the palette's green, **1.19:1** against the worst composite) and its blockquotes (`mdQuote` = yellow, 1.06:1) came out as pale text on a pale sky. Flat, the same palette is only 2.17:1 and 1.93:1 — i.e. it never had text contrast; the picture only made it obvious.

So the two CLIs' emitted token maps get a contrast pass (`legibleTokens`) against the canvas lasso can prove they will be drawn on.

- **The canvas is the WORST one a glyph can land on, not the average** (`glyphCanvasOf`). An image is arbitrary pixels — lasso cannot know what is behind a given cell and a URL a human handed it is not even readable from here — but the scrim bounds the composite: at alpha α the darkest possible cell is `α·bg` and the lightest `α·bg + (1−α)·white`. One of those hurts, and **which one is decided by the THEME** (`Dark`, the same `luminance(bg) > 0.5` test the rest of the sync uses), never by the composite: a light theme under a dim wallpaper must keep pushing its colours darker rather than inverting them halfway through a drag. Clear that bound and every pixel of every image is cleared with it.
- **It scales with the dimming slider by construction.** α = 1 — no image, or a fully opaque wash — collapses the bound onto the theme's own background, so a flat theme is conditioned exactly as before; lowering α widens it and drives the text further. No image decoding, no heuristics, one monotone knob. The palette-derived shading layers are ignored: under an image they sit below the scrim and inside the bound already, and with no image they are two washes at ≤0.16 alpha.
- **Contrast is WCAG's, so it uses WCAG's luminance.** `relLuminanceRGB` (factored out of `omarchy.go`'s `relLuminance`), never `agentsync.go`'s `luminance`, which skips the sRGB linearization: that one answers "light or dark theme?" and is wrong by a factor of two as a contrast input — nord's `#eceff4` on `#2e3440` measures 3.9:1 under it against a true 10.4:1, which had the pass "fixing" text that was already fine.
- **The move is a lightness move in Oklab, hue and chroma held** (`glyphCanvas.legible`, `oklabOf`/`oklabHex`). Mixing toward the background or toward black/white desaturates by however far the hues sit apart (a red collapses to brown while a teal keeps its chroma); moving HSL lightness keeps the hue but bleeds chroma toward either end — measured at 28% of the original left, which is what turned ayu-light's accents into near-neutral mud. Holding `(a, b)` and moving `L` is the literal "same colour, darker", with the sRGB gamut the only thing that may take chroma away (`oklabHex` walks chroma down until the triple fits, keeping L and hue).
- **Two tiers, because a TUI has two kinds of text.** `legibleBody` (4.5:1) for everything carrying words — prose, code, headings, diff markers, syntax, status fields — and `legibleQuiet` (3.0:1) for the deliberately secondary tier (muted, tool output, comments). Collapsing them would cost the hierarchy the interface leans on.
- **Only words are touched, and only when they FAIL.** The tables are keyed by each CLI's OWN token names, not by herdr's palette tokens, because one palette colour lands in both kinds of place: Claude's accent is its `permission` text AND its `promptBorder`, omp's yellow is `mdQuote` and `statusLineGitDirty`. A token absent from the table is left exactly as mapped — every fill, every border and rule, the six diff bands (backgrounds Claude draws text on), and `inverseText` (the theme's background painted ON an accent fill, so this canvas is not the one it needs contrast against). A token already clearing its tier comes back untouched, so a theme whose author had the contrast right is unchanged.
- **A move must be worth making**, and both guards came out of measurement. It may not make text *harder* to read: in the futile regime the bound sits BETWEEN the colour and the pole, so moving poleward crosses it (retro-82's green, 1.62:1 → 1.21:1 at a 0.33 scrim). And it must buy real legibility — below `legibleQuiet` nothing a palette can do makes the words readable, so repainting every accent for a gain from 1.0:1 to 1.3:1 is a theme thrown away for nothing. A dark theme under a bright wallpaper at a third of its dimming is therefore left **entirely alone**; the remedy there is the dimming slider, and leaving the palette alone is what says so.
- **`legibleTravel` (0.75) caps how far a colour may go** toward the pole it is pushed at. Without it the clamped target lands on the pole and every token becomes `#ffffff`: palette gone, hues identical, text no more readable. With it a colour brightens as far as it can while remaining itself (retro-82's `#faa968` → `#ffeadb`, 4.11:1, under a 0.6 scrim). Measured across every theme this build resolves at every dimming: it blocks no conditioning that REACHES its tier on a light theme — the reported case, whose deepest fix travels 0.53 — and there is no cliff either way.
- **A backdrop change now reaches the agents** (`scheduleBackdropResync`, called from `serveUIState`). Picking a picture or moving the slider changes no theme NAME, so nothing used to re-mirror: the files kept a palette conditioned for a backdrop nobody was wearing. It is debounced (1.5s — the slider writes in runs) and re-mirrors the agent theme FILES only (`syncAgentThemesEverywhere`), leaving herdr's `config.toml` and the TUI reload alone: writing the same name fleet-wide and repainting fourteen TUIs per drag buys nothing. omp watches its theme file, so a running agent repaints live.
- **The convergence record carries the backdrop beside the name** (`themeStamp`, `backdropSig`), or a machine asleep through a dimming change would be read as in step for ever — `claimThemeConverge` compares both. A re-mirror only *re-fingerprints* a host lasso has already written this theme to (`restampLegibility`): a host with no record is behind on the theme itself and its next probe owes it `config.toml` too, not just the files this pass touched.

Scope: omp and Claude Code. opencode's generated theme, ghostty's, herdr's own palette and the terminal's ANSI colours are untouched — the same bound would apply, but those were not the report and each is a separate mapping.
