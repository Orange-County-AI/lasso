# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lasso is a Go backend (`src/main.go` and friends) that serves a React/TypeScript SPA. All Go code lives under `src/` (the Go module root — `src/go.mod`). The frontend in `src/web/` is **built and embedded into the Go binary** — `go build` embeds `src/web/dist/`, so it must exist locally (run `mise run build`) but is **not** committed (it's gitignored). CI builds the frontend and produces release binaries.

## Commands

Backend (run from repo root, via [mise](https://mise.jdx.dev); Go sources are in `src/`):
- `mise run build` — builds the frontend then `go build` in `src/` (binary → `./lasso`)
- `mise run dev` — Vite dev server with HMR, proxying to the Go backend (requires tailscale up; auto-bumps the dev port from 8190 if busy)
- `mise run test` — `go test .` in `src/`
- `mise run typecheck` / `mise run lint` / `mise run check` — the frontend checks
- `mise run icons` — re-render the icon set from the vector mark

**Every frontend command runs inside the `dev-lasso` incus container, not on titan.** `bun install`, Vite, tsc and biome are all third-party code, and on the host that code would run as the logged-in user next to the SSH key, the 1Password session and the tunnel credentials. The mise tasks above handle this for you — see `scripts/container.sh`. Do **not** reach past them and run `bun` directly in `src/web/`; that puts the dependency tree back on the host and is exactly what the container exists to prevent. The Go half (`build`, `test`) still runs on the host: Go has no install hooks, and the binary has to be here anyway to drive herdr.

Underlying bun scripts, for reference (invoke via the mise tasks, not directly):
- `bun run dev` / `bun run build` (`tsc -b && vite build`)
- `bun run typecheck` — `tsc -b`
- `bun run lint` — `biome lint .`
- `bun run format` — `biome format --write .`
- `bun run check` — `biome check --write .` (format + lint fixes + import/class sorting)

## Frontend workflow

- Run `mise run typecheck` (`tsc -b` — the project references mean a bare `tsc --noEmit` checks *nothing*, since the root tsconfig has `files: []`) and `mise run lint` before considering frontend work done.
- `src/web/dist/` is the embedded bundle — gitignored and not committed. Run `mise run build` to regenerate it locally; CI builds it for releases.

## Formatting & linting

Tooling is **Biome** (`src/web/biome.json`) — it replaced Prettier + ESLint. Style: 2-space indent, no semicolons, double quotes, ES5 trailing commas, 80-col width. Tailwind class sorting is handled by Biome's `useSortedClasses` (aware of `cn`/`cva`). a11y rules are demoted to warnings (not previously enforced); don't treat them as blocking. Go code: standard `gofmt`.

## Security gotchas

- Never bind to `0.0.0.0`. Use loopback or the tailscale IP. For non-loopback access set `UI_AUTH=user:pass`.
- The file endpoints (`/api/file`, `/api/files`, and the write/rename/delete/upload trio) read and write arbitrary absolute paths as the running user — on the calling tab's host, or on any host lasso may drive when the request names one (`?host=` / a `host` field; see "File viewer host"). Safe only on a private tailnet.
- Running lasso nested inside herdr requires `allow_nested = true` in `~/.config/herdr/config.toml`.
- `/api/push/subscribe` records a URL lasso will POST to unattended, so it is gated by `UI_AUTH` like the rest of the app (deliberately NOT in `withAuthExcept`) and refuses anything that is not `https` with a valid P-256 key. A stored endpoint is a bearer capability to push to that device: it is never returned to a client and never logged — the Settings list and the logs both identify a device by a digest of it (`pushDeviceName`).
- The `/mcp` MCP server is **unauthenticated by default** (exempt from `UI_AUTH` via `withAuthExcept`) — it lets any client that can reach lasso spawn and drive agents. Same trust model as `/api/file`: safe only on loopback / a private tailnet, or behind an edge auth gate (e.g. Cloudflare Access). It introduces no new binding. Set `MCP_OAUTH` (below) to gate it in the origin instead.
- **Unless `MCP_OAUTH` is set**, the origin deliberately implements **no** OAuth (no `.well-known`, no `401`/`WWW-Authenticate`). So OAuth-based MCP clients (Claude Desktop / claude.ai connectors) connecting to `/mcp` over the public hostname require **Managed OAuth enabled on the Cloudflare Access app** — Access then acts as the OAuth 2.1 authorization server (Dynamic Client Registration + auth-code/PKCE), runs the login against the existing Access policy, and issues tokens; the origin still sees an authenticated Access session and needs no auth code. Without it the client's registration fails ("Couldn't register with lasso's sign-in service"). This is an edge setting on the Access application, not a `cloudflared`/tunnel change. `oauth.go` keeps every OAuth route 404 while `MCP_OAUTH` is unset precisely so this Access path stays intact — don't make that metadata unconditional.

## MCP OAuth (`src/oauth.go`)

`MCP_OAUTH=client_id:client_secret` (environment only, like `UI_AUTH` — never argv) turns lasso into a small OAuth 2.1 authorization server for its own `/mcp` resource. Unset = today's open `/mcp`, unchanged.

- **Grants**: `client_credentials` (machine-to-machine — scripts, CLIs, Claude Code; restricted to the `MCP_OAUTH` client and to per-host clients minted with `lasso mcp-client add`, never to an open-DCR registration) and `authorization_code` + PKCE/S256 with `refresh_token` rotation. claude.ai / Claude Desktop custom connectors **cannot** use `client_credentials` — Anthropic's connector infra requires `authorization_code`+`refresh_token` and per-connection user consent — so their "Advanced settings → OAuth Client ID / Client Secret" fields are a *pre-registered client for the auth-code flow*. That's why both grants exist.
- **Routes**: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/oauth/register` (open DCR), `/oauth/token` — all exempt from `UI_AUTH`, since they're the credential-less half of the handshake. `/oauth/authorize` is **deliberately gated** by `UI_AUTH`/Access: that human gate is what makes open DCR safe (anyone may register; nobody gets a token without passing the door and clicking Approve).
- `/mcp` accepts **either** a bearer token **or** the `UI_AUTH` basic credentials, so the CLI and existing callers keep working without an OAuth dance.
- Redirect URIs: DCR clients get exact matching. The pre-registered client accepts any https/loopback callback (a connector's callback isn't known when the secret is minted) and the consent screen displays the exact target; set `MCP_OAUTH_REDIRECT_URIS=<comma-separated>` to lock it to an allowlist.
- Codes and tokens live in `oauth_*` tables in `lasso.db`, stored as SHA-256 hashes, so refresh tokens survive restarts and self-updates.

## Per-tab hosts (`src/reqhost.go`, `src/hostfeed.go`, `src/switch.go`, `src/web/src/lib/host.ts`)

Which host lasso drives is a property of the **browser tab**, not of the process. Two tabs sit on two machines at once; neither disturbs the other.

It used to be one global pointer (`active.b`) that `POST /api/host` swapped, so a switch in one tab moved every other tab's terminal, pane list and file viewer. That pointer survives as the **default host** — the one lasso booted on (`local`, or `-host`) — which answers for any caller naming none: a fresh tab before it chooses, MCP `list_hosts`' `active`, background jobs. It is immutable at runtime.

- **A tab announces itself on every request.** Two carriers, because one cannot cover both call shapes: `fetch` sends the `X-Lasso-Host` header (`hostFetch` wraps every call in `lib/api.ts`), while an `EventSource` and an `<iframe>` src can only carry `?host=`. `requestHost` prefers the query param, so a hand-typed or deep-linked URL is not overridden by the page's own wrapper. `reqBackend(r, explicit)` resolves the backend, with a request's own payload host (the sidebar's `host` field, which follows the FOCUSED pane) winning over the tab's.
- **The tab's choice lives in `sessionStorage`**, seeded from a `?host=` already in the page URL. sessionStorage is per tab by construction, so a new tab starts on the default host instead of inheriting wherever another one wandered, and it survives a reload. `moveTabToHost` attaches server-side, records the choice, then reconnects the SSE stream — in that order, since recording it early would address a host whose terminals are not up yet.
- **`POST /api/host` no longer switches anything.** It *attaches*: pools the host's connection, makes sure its two ttyds are resident, and reports the herdr version/protocol. It mutates no shared state, so two tabs attaching to two hosts is two independent no-ops on each other.
- **One feed per watched host** (`hostfeed.go`). Each runs its own `pane.list` poll, its own herdr event subscription, and its own `panes_rev`/`lastSig`, and pushes only to the tabs watching it. Started on first interest, stopped `feedIdle` (90s) after the last watcher leaves — the poll is herdr's most expensive method, so an unwatched host must cost nothing. **The default host is exempt** and polls for the life of the server, because it is what a fresh tab lands on. Cost is therefore per *watched host*, not per tab: three tabs on titan is still one poller.
- **Theme and UI-prefs revisions stay global**, on the hub, and are stamped into every feed's frames. They are properties of this lasso, not of a host; re-resolving `config.toml` once per watched host would multiply a file read and a fleet-wide theme sync by the number of open hosts.
- **Terminals route by host in the URL**: `/terminal/<slug>/` and `/shell/<slug>/`, each ttyd spawned with its own `-b` base path so its asset and websocket URLs land back on the same instance. The instances were always per host; only the role's `active` pointer had to go. `hostSlug` appends a digest when `sanitizeAlias` alters the alias — with per-host routing a collision means two hosts sharing one terminal, not merely an odd filename. **The reverse proxy's outbound URL host must stay unique per slug** (`<slug>.ttyd.invalid`): `http.Transport` pools keep-alive connections by it, and one shared placeholder served the second host's request down the first host's connection, whose ttyd answered 404.
- **"Is this the active host?" had exactly one answer**, so every guard built on it would now reap a second tab's host out from under it. `hostInUse` (default host, or watched, or holding a resident terminal) replaces it in `reapHostBackends`; `hostWatched` (default or watched, deliberately *not* counting terminals, which would make every terminal exempt from the reaping it decides) replaces it in the ttyd eviction and idle sweeps.
- **The `pane.list` cache is keyed by host**, each entry with its own mutex — sharing one would serve titan's panes under norm's name, and one host's herdr event would drop another's snapshot. Its 400ms TTL runs from when the snapshot was **taken**, not when it landed: the call costs 0.5–1.5s on a busy session, so timing the reply made a listing of the session as it was seconds ago read as fresh. For the same reason `invalidatePaneList` stamps a time **without** taking the entry's lock (which is held for the whole call) and `herdrPaneList` serves the cache only when its snapshot postdates that stamp — a caller coalescing onto an already-in-flight call is usually the one asking about something that has just appeared. `createAgent` invalidates too, so the browser's post-create pane lookup can see the pane it is about to focus.
- **`term_rev` is gone.** It existed to make the browser remount its iframes on a switch; a tab changing host now changes its own iframe `src`, which remounts it.
- **The terminal's palette comes from the DOCUMENT, not the process** (`withLiveTtydTheme` in `src/main.go`). `-t theme=` is read from argv once, so a resident ttyd keeps serving the palette it was spawned under — and nothing retires an instance on a re-theme (killing one drops an open terminal's websocket and its `/shell/` child with it). So the document request is redirected onto `?theme=<live ITheme>`: ttyd's frontend merges options as `{…built-ins, …server-sent, …URL query}`, re-applying the query on every reconnect. This is also what the programs *inside* see — xterm.js answers herdr's OSC 11 background query from the merged theme, which is how omp and opencode infer light vs dark in a pane. The app's own page hid the staleness (`lib/theme.ts` re-pins `window.term.options.theme` from `/api/theme` on every change, which is still what repaints an OPEN terminal); it only showed where nothing repaints from outside, i.e. a browser window opened directly on `/terminal/<slug>/` — which served a cream rose-pine-dawn canvas under dark herdr chrome for hours. Only the document is rewritten (assets, `/token` and the websocket pass through), the redirect is `no-store` (a cached one would pin the palette it was issued under), and a query already naming a theme is passed through so the redirect cannot loop.

## Theme atmosphere (`src/web/src/index.css`, `src/web/src/lib/theme.ts`, `src/web/src/lib/wallpaper.ts`, `src/web/src/lib/mode.ts`, `src/db.go`, `src/hostpanes.go`)

**Any** theme can wear a **backdrop**, and a backdrop is a real image. Three sources feed one gallery (Settings → Themes): the 27 Retro 82 stills lasso vendors as WebP under `src/web/public/wallpapers/retro-82` (longest edge 1920, plus 320px thumbs; provenance in that directory's `NOTICE.txt`) and describes in `src/web/src/lib/retro82-wallpapers.json`; whatever a theme shipped with, served by the Go side as root-relative `/omarchy/bg/<theme>/<file>` with a 320px `/omarchy/thumb/...` preview beside it (`GET /api/omarchy-themes` → `backgrounds`/`thumbs`, two positionally-parallel arrays zipped by `shippedPairs`); and pictures a human handed lasso by URL or upload. Palette hexes come from `/api/theme`, never from CSS.

- **The two shipped sources are exclusive, not additive.** Where lasso bundles a set (retro-82) it wins outright and the catalog's own images for that name are skipped: upstream's set is the same *pictures* under different filenames, so merging would offer every still twice under two labels and a URL dedupe cannot see it. The bundled copy is also the superset, and the one with real thumbnails.
- **Nothing is authored in CSS but the rules that read two custom properties.** `lib/theme.ts:applyAtmosphere` composes the whole `background-image` stack — scrim over shading over `url(...)` — and pins it as `--atmo-layers`, with the theme's own terminal background as `--atmo-base`, on `<html>`. `index.css` then has one body rule (`:root[data-atmosphere] body`) that paints `var(--atmo-base)` + `var(--atmo-layers)` fixed/cover, and `termAtmosphereCSS` mirrors the same two values into each ttyd document. One composition, two documents. The attribute is matched on **presence** (its value is the theme name, for inspection only) because every theme is now a candidate.
- **A backdrop is an explicit pick, per theme, and it belongs to the SERVER.** It lives in lasso's own `ui_state` blob (`theme_atmosphere`, `custom_backgrounds` in `db.go`) and rides the machinery the sidebar and the usage footer already use: a patch `POST /api/ui-state`, a `ui_state_rev` bump on every save, one React Query cache per tab, `syncUIState` on the bump. So a still picked on a phone paints on the desktop within a beat and with no reload, and a browser that has never been told anything wears what the last human chose. Nothing reaches `config.toml` and nothing is mirrored to another host — this is lasso's UI state, not the shared herdr theme, which is exactly why the browser-local *palette* choice (`lib/mode.ts`) stays in `localStorage` while the backdrop for it does not. Keyed by the theme the BROWSER resolved, so switching palette restores the backdrop each one had. Only retro-82 has a default (`04-dusk-guardian`); every other theme starts flat, since a palette switch must not drop a photograph on you. An unknown stored URL — a still dropped by a later vendoring, a custom picture since forgotten — resolves back to that default instead of pointing the backdrop at a 404. **There is no import from the old `localStorage` keys**: a browser's private copy cannot be told apart from a stale one, and letting one seed the shared state would have the last tab to open decide the fleet's backdrop. Re-pick once; every device follows.
- **Merged per theme AND per field, because this is the first part of `ui_state` two humans edit at once.** A JSON decode over the stored struct merges top-level fields, but a map's named entry is REPLACED wholesale — so `serveUIState` detaches both collections before the decode and rebuilds them (`mergeThemeAtmosphere`, `mergeCustomBackgrounds`). Two levels, two races: a laptop dressing rose-pine must not drop what a phone just picked for retro-82 (entry level), and a nudge of the dimming slider must not drop that theme's picture (field level, which is what the `*float64`/`*bool` pointers are for). Detaching them also keeps the decode from writing through the map `stored` still points at, which would make the no-op check that guards the rev bump compare the merge against itself — a 200 with nothing saved. No layout-style claim is needed: unlike the sidebar, nothing re-persists a backdrop unprompted.
- **Only explicit choices are stored, and nothing paints until they arrive.** An absent entry means the frontend's default, never a value written back — so a tab whose fetch is still in flight cannot persist a default over a choice it has not seen. `lib/wallpaper.ts` reports no image and no shading until `uiStateSettled()` (arrived, or failed — a dead endpoint degrades to the defaults rather than to a terminal that never gets its palette pinned), because the alternative is the default photograph appearing and vanishing on a browser whose owner turned it off.
- **A hand-given picture is remembered globally, not per theme** (newest first, capped at 24 on both sides): a photo you like is a property of your screen, and now of this lasso. A URL is used verbatim; an absolute path is read back through `/api/file?path=…&host=…`; an upload goes through `/api/paste-file` (the endpoint terminal paste/drop already uses) and is then referenced by that same `/api/file` URL — so it survives a reload, where a `blob:` URL would not, without lasso growing an image store. It is written as an OP (`remember_background` / `forget_background`), never as a list: a tab sending the whole gallery out of a copy it fetched minutes ago would resurrect a picture another browser just forgot. Only these can be forgotten; a bundled or shipped one belongs to the theme.
- **The scrim is derived, not authored.** `rgba(<theme background>, alpha)`, with `alpha` the Settings "image dimming" slider — default **0.70**. The reset button beside the slider restores this default; existing saved values remain unchanged until reset. It is the outermost layer of the stack, so it washes the image *and* the shading below it, and it is left out entirely when no image is picked (there is nothing to wash). A palette whose background is not a plain `#rrggbb` yields no scrim rather than a guess.
- **Palette shading is the imageless backdrop** (`getShading`, **on** unless a theme's entry says otherwise): two very low-alpha radial washes of the theme's own `blue`/`magenta` (falling back to `cyan`/`green`), one from the top-left, one from the bottom-right. It is what gives a flat theme depth, and it turns the terminal transparent exactly like an image does.
- **Translucency is always a `background-color` with alpha, never `opacity`.** `opacity` would fade the glyphs with the surface, which is the whole thing being avoided: text stays fully opaque everywhere.
- **A surface that COVERS the backdrop reproduces it instead of going flat** (`index.css`, `.chat-overlay .vsurface`). The chat, its agent column and its agent sheet must be opaque — they sit over the terminal, and at `--background`'s 62% herdr's own tab bar and text read straight through the conversation — but flat was the wrong opaque: the shading, or the whole backdrop, stopping dead at the chat's edge made the conversation read as a deader surface than the chrome around it, and the Settings shading and dimming controls visibly reached everything except the place the eye spends its time. So those surfaces paint what the body paints — `--atmo-base` under `--atmo-layers`, fixed and cover so the image lands at the same coordinates and the two meet seamlessly at the panel's edge — which is a painting of the backdrop rather than a window onto it: nothing behind can read through, and everything inside (the `--background` root, the `--card` composer and cards) floats on it exactly as the chrome does. The file viewer and the Files panel's empty state keep the flat fill, being reading surfaces with nothing to be continuous with, and `--popover` is still solid.
- **The terminal's backdrop is CSS, not an xterm color.** `applyTermAtmosphere` injects it into each ttyd document (a parent stylesheet does not cross the iframe boundary — the same reason `applyTermFont` re-declares the `@font-face` there), reading the values off the parent's own custom properties so there is one definition. xterm is handed a fully transparent default background and `allowTransparency: true`, so a cell no program has colored paints nothing. Keeping the scrim in CSS makes the tint identical under all three of ttyd's renderers instead of depending on how each composites a half-transparent theme color; ttyd's own `<body>` is neutralized rather than used for the wash, since a second painted surface over a scrim layer would double the tint. Every URL emitted is root-relative or absolute, which is what makes the same string resolve inside a document served from `/terminal/<slug>/`.
- **`applyAtmosphere` is the single chokepoint, and it repaints in place.** `refreshTheme` calls it (so a reload, a re-theme and an appearance change all land there) and so does `subscribeAtmosphere` — a subscription to the persisted prefs' query cache, which fires for a pick made HERE (the optimistic write) and for one made in another browser (the `ui_state_rev` refetch) alike, so no Settings control has to remember to repaint. It compares only the atmosphere slice of `ui_state`, since the same cache entry carries `sidebar_pct`, which a drag rewrites dozens of times a second. `applyTermAtmosphere` **updates** an already-injected stylesheet whose text differs rather than skipping on its presence, and writes nothing when it doesn't, so a pick repaints the chrome *and* every already-loaded terminal iframe with no remount and the reconcile stays free. Before the first palette has resolved it does nothing at all: a pick made while `/api/theme` is in flight is already persisted, and painting a black canvas meanwhile would be a flash of a theme nobody chose.
- **`allowTransparency` is what makes glyphs work.** Without it xterm bakes the background behind each glyph into its texture atlas and every cell becomes an opaque tile. It is pinned in `applyTermTheme` — the one place boot, a re-theme and the post-reconnect reconcile all funnel through — and xterm rebuilds the atlas on the change (the docs' "must be set before `open()`" is stale for 5.3; verified against a live webgl renderer). Writing an unchanged boolean is a no-op in xterm's option setter, so a flat theme pays nothing.
- **The palette and that boolean are one pin, and both halves read the LIVE cache.** `applyTermTheme` takes no theme argument and each retry re-reads `lastXtermTheme`: a snapshot captured before a `setTimeout` outlives the palette it came from, so switching a backdrop theme → a flat one while an iframe is still connecting would land the queued palette — background transparent — under the flat theme's `atmosphereOn=false` pin a quarter second later, i.e. blank tiles until the next reconcile. `reconcileTermTheme` compares `allowTransparency` alongside the background for the same reason: either can drift alone, and half a pin is a broken terminal rather than a mismatched one.
- **The transparent background still has to spell out the theme's own background** (`<theme bg>00`, e.g. `#00172e00` under Retro 82), and that is what makes the backdrop visible *inside herdr's panes* rather than only at its edges: xterm answers OSC 11 with the alpha dropped, herdr records that as the host terminal's background, and its pane renderer emits **no** explicit background for a cell whose default matches the host's (`ghostty_default_bg` → `None` → `Color::Reset`). A different RGB would make herdr paint every pane cell explicitly and the backdrop would never show. It is also the reply omp and opencode read to infer light vs dark, so it must keep the theme's own lightness. A palette whose background is not a plain `#rrggbb` gets no transparency at all — a normally painted terminal, not a broken one.
- **What stays opaque is opaque, by definition.** A cell carrying its own SGR background cannot be made translucent from the outside: herdr's tab bar, status/overlay bars, dialogs and active-row highlights all paint `panel_bg` (the theme's own panel color, so they read as calm flat bands rather than a clash), and so does any TUI that colors its own canvas. herdr's desktop sidebar is `sidebar_bg = Color::Reset` in every built-in theme — deliberately left unset by the override block lasso writes — so it shows the backdrop, and so do a pane's own default cells (`mode=0`, no bg). Worth knowing when checking this by hand: a full-screen herdr overlay (onboarding, settings) paints `panel_bg` edge to edge, so with one open the whole terminal reads opaque and the backdrop looks broken — close them before concluding anything about transparency.
- **A standalone `/terminal/<slug>/` window gets the palette but no backdrop.** The injection is the app page's; nothing else runs in that document. Same class of gap as everything else `lib/theme.ts` reaches in to do.
- **The chrome half is gated twice**: `data-atmosphere` lands on `<html>` only when the effective theme HAS a backdrop AND the chrome is actually following a palette (`chromeFollowsPalette` — appearance mode `herdr`, or a palette named for the scheme in force), since the Nothing light/dark canvases are flat monochrome by design. So a flat-chrome tab still shows the backdrop in its terminals and says so in Settings. Everything keyed off the attribute is additive (body backdrop, translucent `--background`/`--card`/`--sidebar`, the accent hairline on `.term-shell`, which now mixes from the live `--h-*` rather than retro-82's amber and teal), so dropping it restores the chrome exactly — and `--popover` is deliberately never translucent, a menu being a reading surface.

### Appearance and palettes (`lib/mode.ts`, `lib/theme.ts:refreshTheme`, `lib/ui-state.ts`)

What the chrome is painted from is **server state**, not a per-browser choice: `appearance_mode` (`herdr`|`system`|`light`|`dark`, default `herdr`) plus `palette_light`/`palette_dark` are three flat fields of `ui_state`, so they ride the patch-merge, the React Query cache and the `ui_state_rev` SSE bump the backdrop and the usage footer already use. Pick Dark on a phone and the desktop repaints within a beat; a fresh browser opens on what the last human chose. Nothing about appearance is in `localStorage` — the keys `lasso-mode`, `lasso-palette-light` and `lasso-palette-dark` are gone and deliberately **not** imported, since adopting one browser's stale choice as the new fleet-wide answer is a worse first impression than the documented default.

The herdr theme itself is a different thing and stays shared *with herdr*: `POST /api/theme-set` writes `[theme].name` in `config.toml`, the TUI reloads, every tab follows the `theme_rev` bump, and lasso mirrors it to the synced hosts and agent CLIs — **while no appearance palette is named**, the one case that refuses the write (`fleetThemeIsPalette`, below). Resolving a palette is therefore a **read** — nothing about a repaint may re-theme the fleet — but an appearance change *made in a browser* pushes the palette it resolved (see "Pushing a resolved palette to the fleet" below), because the agents inside a terminal have to match the terminal.

- **`system` is stored, its ANSWER is per device.** The OS scheme is an observation about the screen in front of someone, not a preference to share, so `resolvedMode` collapses the stored `system` against each browser's own media query. Everything else resolves identically everywhere.
- Outside `herdr` mode lasso may name a theme **per scheme** (`localPaletteName()` collapsing the two fields against `getMode()`/`resolvedMode()`), and `refreshTheme` resolves it through **`GET /api/theme?name=`** — a read: `refreshTheme` writes nothing, whatever called it. That payload paints the chrome *and* the terminals. `""` (every existing install) means the flat Nothing chrome and herdr's shared palette in the terminals — the previous behavior, unchanged.
- **One request either way.** `refreshTheme` asks for the named palette when there is one and falls back to plain `/api/theme` if that fails (an uninstalled theme, an older server), so a stale preference degrades to the shared look rather than to no theme.
- **An arriving change repaints through the same chokepoint a local pick does.** `subscribeAppearance` compares only the three-field slice of the cache (plus whether it has settled) and `AppProvider` hangs `refreshTheme` off it — the full repaint: html class, `--h-*` override, every terminal iframe's palette, the backdrop. It is read-only, so a change delivered by SSE cannot echo back out as a write, and nothing remounts. The Settings controls read the same cache (`useUIState()` + `getMode()`/`getPalettePref()`) instead of copying it into React state, which is what used to leave the buttons showing this tab's own choice after another browser changed it.
- **Nothing is readable before first paint any more**, so `index.html` carries a static `class="dark"` — the DEFAULT mode's scheme, matching `DEFAULTS` in `lib/ui-state.ts` and `getUIState` in `db.go` — and `lib/mode.ts` re-asserts the class the moment `/api/ui-state` lands. A lasso pinned to Light therefore opens dark for that one round trip. Do not "fix" this with a localStorage mirror: two sources of truth for the same field is the bug this replaced.
- **The OS flip has to re-run `refreshTheme`, not just the class.** `watchSystemMode(onChange)` takes a callback (`AppProvider` passes `refreshTheme`) because the media-query change also changes WHICH palette applies; `lib/mode.ts` cannot import `lib/theme.ts` itself, that being the direction of the existing dependency. `lib/mode.ts` → `lib/ui-state.ts` → `lib/api.ts` is acyclic, which is why the mode can live on server state at all; `AppearanceMode` is declared in `lib/api.ts` (with the payload) and re-exported as `Mode`.
- **The `--h-*` override is written as `:root:root{…}`.** `index.css` declares the light tokens on `:root.light`, which outranks a plain `:root` no matter where it sits in the cascade — invisible while only `herdr` mode (dark class) used the override, and a silently ignored palette the moment a *light* one exists.
- **Each scheme's picker only offers themes of that lightness.** A light palette under the dark class leaves every `dark:` variant in the chrome fighting the palette it sits on, and the html class stays the OS/pinned scheme's.
- **Never send `appearance_mode: ""`.** The server answers 400 and drops the WHOLE patch (see `src/appearance_test.go`); clearing a *palette* is `""`, clearing a mode is not a thing.
- **A theme installed from a URL** (`POST /api/omarchy-themes {url}`) answers with the whole catalog: the Settings pane writes it straight into `qk.themeCatalog`, drops `lib/theme.ts`'s own module-level catalog cache (`invalidateThemeCatalog`) and re-resolves the palette, since an install can hand the theme already on screen a set of images. That cache is deliberately kept for the page's life — including a FAILED fetch, cached as an empty list, so an older server is not asked again on every re-theme. Uninstalling is not offered: the clone is a directory on the machine, and deleting one from a browser is a footgun with no undo.

#### Pushing a resolved palette to the fleet (`lib/mode.ts:pushPaletteToFleet`)

The palette a browser resolves is one value; the theme lasso **writes** — herdr's `config.toml` plus every agent CLI's own theme file (`src/agentsync.go`) — is another, and nothing connected them. So picking a light palette repainted the chrome and the terminals `ayu-light` while omp, opencode, Claude Code and herdr's own tab bar kept whatever the herdr theme picker last set: retro-82 navy panels drawn on a cream canvas. The Settings **"Sync now"** button was the only thing that closed it, by hand.

`pushPaletteToFleet` now makes an appearance change call the same endpoint that button does (`POST /api/theme-sync {palette, quiet}` → `setLocalHerdrTheme` + `syncThemeNow`).

- **Only from the three entry points where THIS device is the cause** — `setMode`, `setPalettePref`, and the `watchSystemMode` OS flip. Never from `refreshTheme`, which also runs for a change that *arrived* over `ui_state_rev`: a push bumps `theme_rev` and repaints every other browser, so pushing from a repaint would have two devices resolving `system` differently re-theme each other forever. The last human to act decides — which is what asking the fleet to follow your screen means, and it is the same `user_intent` distinction `uilock.go` draws for the sidebar.
- **`""` is skipped.** That is `herdr` mode, whose whole meaning is that the fleet's own theme wins; pushing it would be a fleet-wide SFTP write of what is already there.
- **Debounced 500ms, with one retry at 3s.** The controls are clicked in runs (mode, then the palette for it) and the server refuses a second fanout while one is in flight (`themeSyncRunning`, 409). A dropped push is **not** self-healing: `convergeThemeOnProbe` catches a host up against the theme lasso last *wrote*, and a push that never landed never became that. After the retry the remembered palette is cleared so the next appearance action tries again instead of reading as already pushed.
- **`quiet` drops the SUCCESS notice only.** A "synced to 14 hosts" toast arriving fleet-wide seconds after every appearance click is noise; a host that *refused* the write is the one thing a human has to be told, and nothing else would tell them.
- **A palette in force takes the herdr picker off the table.** Both are the same single value, so while one is named `POST /api/theme-set` answers 409 and the Settings select is held with a line saying why (`lib/mode.ts:fleetThemeIsPalette` mirrors the server's `fleetThemeIsPalette`). A pick there would fan the theme no screen is showing out over the palette every screen is, and leave it there: the fan-out and the per-probe convergence both read what lasso wrote to herdr's `config.toml`, so herdr's config has to keep holding the palette for the fleet to stay on it. `herdr` mode — whose whole meaning is that the fleet's own theme wins — keeps the picker authoritative whatever palettes are stored; a pinned mode answers for its own scheme only (a light palette under pinned dark governs nothing); `system` counts a palette named for either, since the server cannot see which scheme a device resolved. Clearing the palette hands the fleet back to the picker, and `pushPaletteToFleet`'s `""` branch forgets what it pushed so the picker's next move is not read as already synced.
- **An edit lasso did not make is not adopted either.** The hub poll (`hub.refreshTheme`) re-resolves `config.toml` every `-poll` (2s) and, while a palette governs, refuses a theme lasso did not write: `herdr`'s own theme popup and a hand edit are seen, logged once per value (`theme: herdr's config.toml names "x", which lasso did not write; an appearance palette governs, so the fleet stays on y`), and dropped. It has to be "not adopted" rather than "adopted but not fanned out": `convergeThemeOnProbe` pushes the HUB's theme to every host that is behind, so adopting the edit would put the fleet on it within a probe sweep whatever the fan-out does — keeping the hub on the palette is what keeps the fan-out, the convergence and every browser that follows herdr on it. Lasso's own writes are still adopted, told apart by the record of what it last wrote to the local machine (`themeSynced.by["local"]`, which `setLocalHerdrTheme` marks *before* it re-resolves — the fan-out that would otherwise mark it has not run yet). One residual, deliberately: a stray edit that predates the boot is adopted, because that record is in memory and a restarted lasso has no note of its own writes.

### Legible agent text under a backdrop (`src/legibility.go`, `src/agentsync.go`)

A backdrop changed what a pane's glyphs land on and nothing downstream noticed. The terminal under one is served transparent (`transparentPanelBG`), so an agent's own cells show a photograph washed by the scrim, while omp's and Claude Code's generated themes were still mapped straight off the palette — colours an author chose against a flat canvas. Ayu Light under a wallpaper at 0.75 dimming was the report: omp's inline code (`mdCode` = the palette's green, **1.19:1** against the worst composite) and its blockquotes (`mdQuote` = yellow, 1.06:1) came out as pale text on a pale sky. Flat, the same palette is only 2.17:1 and 1.93:1 — i.e. it never had text contrast; the picture only made it obvious.

So the two CLIs' emitted token maps get a contrast pass (`legibleTokens`) against the canvas lasso can prove they will be drawn on.

- **The canvas is the WORST one a glyph can land on, not the average** (`glyphCanvasOf`). An image is arbitrary pixels — lasso cannot know what is behind a given cell and a URL a human handed it is not even readable from here — but the scrim bounds the composite: at alpha α the darkest possible cell is `α·bg` and the lightest `α·bg + (1−α)·white`. One of those hurts, and **which one is decided by the THEME** (`Dark`, the same `luminance(bg) > 0.5` test the rest of the sync uses), never by the composite: a light theme under a dim wallpaper must keep pushing its colours darker rather than inverting them halfway through a drag. Clear that bound and every pixel of every image is cleared with it.
- **It scales with the dimming slider by construction.** α = 1 — no image, or a fully opaque wash — collapses the bound onto the theme's own background, so a flat theme is conditioned exactly as before; lowering α widens it and drives the text further. No image decoding, no heuristics, one monotone knob. The palette-derived shading layers are ignored: under an image they sit below the scrim and inside the bound already, and with no image they are two washes at ≤0.16 alpha.
- **Contrast is WCAG's, so it uses WCAG's luminance.** `relLuminanceRGB` (factored out of `omarchy.go`'s `relLuminance`), never `agentsync.go`'s `luminance`, which skips the sRGB linearization: that one answers "light or dark theme?" and is wrong by a factor of two as a contrast input — nord's `#eceff4` on `#2e3440` measures 3.9:1 under it against a true 10.4:1, which had the pass "fixing" text that was already fine.
- **The move is a lightness move in Oklab, hue and chroma held** (`glyphCanvas.legible`, `oklabOf`/`oklabHex`). Mixing toward the background or toward black/white desaturates by however far the hues sit apart (a red collapses to brown while a teal keeps its chroma); moving HSL lightness keeps the hue but bleeds chroma toward either end — measured at 28% of the original left, which is what turned ayu-light's accents into near-neutral mud. Holding `(a, b)` and moving `L` is the literal "same colour, darker", with the sRGB gamut the only thing that may take chroma away (`oklabHex` walks chroma down until the triple fits, keeping L and hue).
- **Two tiers, because a TUI has two kinds of text.** `legibleBody` (4.5:1) for everything carrying words — prose, code, headings, diff markers, syntax, status fields — and `legibleQuiet` (3.0:1) for the deliberately secondary tier (muted, tool output, comments). Collapsing them would cost the hierarchy the interface leans on.
- **Only words are touched, and only when they FAIL.** The tables are keyed by each CLI's OWN token names, not by herdr's palette tokens, because one palette colour lands in both kinds of place: Claude's accent is its `permission` text AND its `promptBorder`, omp's yellow is `mdQuote` and `statusLineGitDirty`. A token absent from the table is left exactly as mapped — every fill, every border and rule, the six diff bands (backgrounds Claude draws text on), and `inverseText` (the theme's background painted ON an accent fill, so this canvas is not the one it needs contrast against). A token already clearing its tier comes back untouched, so a theme whose author had the contrast right is unchanged.
- **A move must be worth making**, and both guards came out of measurement. It may not make text *harder* to read: in the futile regime the bound sits BETWEEN the colour and the pole, so moving poleward crosses it (retro-82's green, 1.62:1 → 1.21:1 at a 0.33 scrim). And it must buy real legibility — below `legibleQuiet` nothing a palette can do makes the words readable, so repainting every accent for a gain from 1.0:1 to 1.3:1 is a theme thrown away for nothing. A dark theme under a bright wallpaper at a third of its dimming is therefore left **entirely alone**; the remedy there is the dimming slider, and leaving the palette alone is what says so.
- **`legibleTravel` (0.75) caps how far a colour may go** toward the pole it is pushed at. Without it the clamped target lands on the pole and every token becomes `#ffffff`: palette gone, hues identical, text no more readable. With it a colour brightens as far as it can while remaining itself (retro-82's `#faa968` → `#ffeadb`, 4.11:1, under a 0.6 scrim). Measured across every theme this build resolves at every dimming: it blocks no conditioning that REACHES its tier on a light theme — the reported case, whose deepest fix travels 0.53 — and there is no cliff either way.
- **A backdrop change now reaches the agents** (`scheduleBackdropResync`, called from `serveUIState`). Picking a picture or moving the slider changes no theme NAME, so nothing used to re-mirror: the files kept a palette conditioned for a backdrop nobody was wearing. It is debounced (1.5s — the slider writes in runs) and re-mirrors the agent theme FILES only (`syncAgentThemesEverywhere`), leaving herdr's `config.toml` and the TUI reload alone: writing the same name fleet-wide and repainting fourteen TUIs per drag buys nothing. omp watches its theme file, so a running agent repaints live.
- **The convergence record carries the backdrop beside the name** (`themeStamp`, `backdropSig`), or a machine asleep through a dimming change would be read as in step for ever — `claimThemeConverge` compares both. A re-mirror only *re-fingerprints* a host lasso has already written this theme to (`restampLegibility`): a host with no record is behind on the theme itself and its next probe owes it `config.toml` too, not just the files this pass touched.

Scope: omp and Claude Code. opencode's generated theme, ghostty's, herdr's own palette and the terminal's ANSI colours are untouched — the same bound would apply, but those were not the report and each is a separate mapping.

## Sidebar-layout ownership (`src/uilock.go`, `src/web/src/lib/sidebar.ts`, `src/web/src/lib/ui-state.ts`)

`ui_state` is merged per field and broadcast to every tab, which is right for everything a human clicks — the usage footer, the Files tab's click behavior. The sidebar layout is not that: **every tab re-persists `sidebar_collapsed`/`sidebar_pct` from its own panel group without anyone asking it to** — on mount, on a window resize, and on the programmatic apply of a change that arrived over SSE. That makes the layout a shared variable that any number of clients write on their own initiative, and one stale client is enough to reopen a sidebar the human just collapsed, indefinitely:

> tab A collapses → `ui_state_rev` → tab B applies → B's panel bounces back open (its own remembered layout, its own viewport) → B persists "open" → `ui_state_rev` → A reopens.

So those two fields are arbitrated by an in-memory claim instead of merged. **The most recently active client owns them.**

- **`user_intent` is the whole distinction, and only the client can report it.** A panel group reports a drag and a remount through the same `onResize` callback, so the server cannot tell a change someone MADE from one a tab merely arrived at. `lib/sidebar.ts` stamps intent at the user-driven entry points (⌘\, the collapse/expand chevrons, the mobile dial, and `beginSidebarDrag` on the handle) and the debounced persist asks whether a stamp landed recently enough to be the cause. A drag re-stamps on `pointerup` — bound on `window`, since a drag routinely ends elsewhere — because a slow drag would otherwise outlive the 2s window and settle unattributed.
- **Only two writers may move the sidebar**: a client whose human just acted (it takes the lock from whoever held it), or the current owner within `layoutLease` (45s) settling the change it just made. Everything else is refused. **A free lock is deliberately NOT a third**: an expired lease must not promote an unattended echo into an authority, because "nobody has touched a tab in a while" is exactly the state the rogue client writes in. An unheld lock just means the next human to act gets it uncontested.
- **Arbitrated on the difference, not on the field's presence.** A client restating the layout it already agrees with is asking for nothing; answering that with a refusal would snap its panel to a value it is already rendering, on every routine echo.
- **A refusal drops only those two fields.** The rest of the patch is that client's own deliberate change and still lands, so collapsing the usage footer from a tab that lost the sidebar claim still works.
- **A refused write neither saves nor bumps `ui_state_rev`** (the handler skips both when the merge changes nothing), so a client losing a fight cannot make every other tab refetch on each round of it. The loser also backs off `DENY_BACKOFF_MS` (30s) before offering the layout again — its panel group will keep producing the refused size, that being what makes it rogue — and a human acting in that tab lifts the backoff immediately.
- **The claim is in memory, never in the db.** It is a property of the clients currently connected; a restart should leave nobody holding it rather than let a client that has since gone away keep writing through a resurrected claim.
- **`client_id` identifies the TAB** (sessionStorage, like the tab's host), because two tabs on one machine are two clients that can disagree. It is generated without `crypto.randomUUID` when that is unavailable — lasso is routinely reached over plain http on a tailnet address, which is not a secure context. **A client sending no id can never move the sidebar for anyone**: that is a tab built before this handshake, whose writes are indistinguishable from the unattended ones this exists to stop. Its own view still works; it stops syncing until reloaded.
- **No toast on refusal.** A human's change always wins the claim, so the only writes that can ever be refused are ones nobody asked for.

### The write pipeline (`lib/ui-state.ts`)

Every `ui_state` field is now something the UI paints itself from — the appearance mode, the palettes, the backdrop — so a save that silently failed is a tab wearing a theme nobody stored, and a response arriving out of order is a theme nobody chose.

- **One save on the wire at a time.** A response is ADOPTED (below), and two concurrent saves settle in whatever order the network gives them, so the slower one would write the older merge over the newer. A patch offered while a save is in flight is merged into the single pending slot and sent when it settles; a merged patch and a queue of patches reach the same stored state, and the merged one cannot arrive out of order.
- **An immediate write does not jump the coalescing timer.** The dimming slider coalesces at 250ms while the reset beside it writes at once — sent as-is, the last slider tick would land AFTER the reset and undo it. So `coalesceMs: 0` cancels the timer, merges over what was waiting, and sends one patch.
- **The acknowledged body is adopted**, which is how a field another browser changed lands without waiting for the SSE bump, and how a refused layout gets put back where its owner has it. Skipped when `writeSeq` moved or a patch is pending — that change is not in this body, and the follow-up write's own response carries both — so adoption can never revert what the human is looking at.
- **A failed save says so** (one toast id, so a drag's worth of failures is one line) and then converges by RE-READING `/api/ui-state` rather than unwinding the patch: a snapshot rollback would also discard every other field that changed meanwhile. If the re-read fails too (lasso unreachable) it retries every 5s until one succeeds — nothing bumps `ui_state_rev` for a write that never landed, so without that the tab would sit on the optimistic value forever.

## Agent visibility scope (`src/hostscope.go`, `src/callerscope.go`, `src/groups.go`, `src/mcpgroup.go`)

Two bounds decide which agents an MCP caller can see and message. Both apply. A third layer, groups, widens the second.

1. **What lasso can address** (`hostscope.go`) — the local box plus the concrete aliases in the ssh config lasso reads. Membership is the config's, never the agents db's, so a host whose alias was removed stops being listable/addressable instead of resolving to a target no call can reach. Reachability is deliberately *not* part of it: an alias whose box is asleep still resolves and gets an honest "unreachable" from the backend.
2. **What this caller may address** (`callerscope.go`) — per-credential. `lasso mcp-client add --host <alias>` mints one OAuth client per host; the resolved host rides `auth.TokenInfo` into every tool call, so a caller's host is derived from its token and cannot be asserted. Scope defaults to `self` (that host only); `--fleet` opts a trusted host up to the whole addressable set. `lasso mcp-client token <client_id>` mints a bearer token for clients that can only carry a header (`claude mcp add --header …`) — **no expiry by default**, since it sits unattended in a host's config where a rolling expiry is an outage on a timer; `--ttl 90d`/`2w`/`12h` for a dated one. Never-expiring tokens are stored with an empty `expires_at`, which `purgeExpiredOAuth` excludes explicitly (`''` sorts before every timestamp in SQLite) and `mcpTokenVerifier` translates into a synthetic future `Expiration`, because `auth.RequireBearerToken` rejects a zero one. Unidentified callers (no bearer token — open `/mcp`, or the `UI_AUTH` basic escape hatch) are fleet-scoped, which is the historical behavior.
3. **Groups** (`groups.go` resolution, `mcpgroup.go` CLI, `mcp_group*` tables) — the middle ground between `self` and `fleet`, purely **additive on top of `self`**: no new scope value, no `oauth_clients` change, `Fleet` still short-circuits first. Members are **hosts** (aliases or `local`), not credentials, so membership survives re-keying. Reach within a group's member closure is mutual; asymmetry comes from directed, **non-transitive** grants `A→B` (one hop). Nesting `@H` in `G` makes H's hosts mutual with all of `closure(G)` — grant, don't nest, if that is not the intent. `mcpTokenVerifier` resolves a self-scoped caller's reach **per request** into `TokenInfo.Extra["lasso.reach"]`, so group edits land on the next tool call with no re-mint and no session restart. Runbook and CLI: `docs/mcp-agent-scope.md`.

Consequences worth knowing:

- **Containment requires `MCP_OAUTH`.** With it unset, `withMCPAuth` is a no-op and every caller is unidentified, so provisioned per-host credentials — and the groups built on them — are inert; startup logs a warning saying exactly that.
- `host` now defaults to the **caller's own** host, not `local`. `local` means the box lasso runs on, which for a remote agent is someone else's machine; the old default silently pointed every remote caller at the lasso host's agents.
- `whoami`/`close_agent` keep "empty host = search every host I may reach" (`searchHost`, not `hostOr`), except that an identified caller collapses the search to its own host — which also retires the cross-host pane-id collision refusal. Groups reopen that only for `close_agent`, and only when the caller's reach spans more than its own host: `whoami` stays pinned to `cs.Host` (a caller's own pane is on its credential's host by definition). The empty-host `adoptPeerAgent` fallbacks are guarded by `cs.allows("local")`, or a group caller whose reach excludes local could close a local pane through them.
- MCP identity is **not** a sandbox. A fleet-scoped agent can proxy for a contained one, and a secret in a pod can be exfiltrated. If a trust zone is a real boundary, block the pod's network path to lasso and treat this as defense in depth.
- The spec offers nothing here: as of MCP 2025-11-25 `clientInfo` is a self-asserted name/version/title, no header identifies the caller, and the spec's own session-hijacking guidance is that the principal must be "derived from the user token and not provided by the client". Hence per-host credentials rather than a `host` argument or an `_meta` claim.

## Agent record reconciliation (`src/agentreap.go`)

The `agents` table is an append-only log; herdr's panes are not. Nothing used to compare them, so every agent whose pane was closed left a record that still read as live and "ready" — 139 records against herdr's 8 on titan — and each one was listed, unmessageable, and un-closeable (`pane_not_found` / `workspace_not_found`), with no route to clear it through the API.

`reconcileHostAgents(host, panes)` stamps `closed_at` on the records a successful pane enumeration contradicts. It is called from the two places that already hold a fresh per-host pane listing — `fetchAllPanes`' success branch (the aggregation, driven by the reaper on an interval and by any `/api/all-panes` caller) and `listAgentsTool` (before it reads the records) — rather than from a timer of its own, which would have to re-enumerate every host to learn what those two already know.

- **`startAgentReaper` keeps it happening with nobody looking** (`agentreap.go`). The aggregation reconciles as a side effect of being fetched, and once the browser stopped fetching it — the pane palette that polled it is deleted — an MCP `list_agents` was the only remaining caller, which left a lasso nobody was driving with records that never caught up. The reaper therefore drives `panesSnapshot` itself (`agentReapEvery`, 5m): it reconciles nothing directly, it asks the same cached aggregation `/api/all-panes` serves, whose per-host success branch is where the "did herdr actually answer" distinction lives. One pass runs at startup — a lasso that just came up has no idea what became of its agents while it was down — and the two-miss rule means that pass can condemn nothing on its own. It is hygiene rather than correctness: every MCP reader reconciles its own enumeration anyway, so what the interval bounds is how long a record can sit un-tombstoned when nobody has asked.
- **Marked, not deleted.** The row is both "which agents are there" (where a dead one is noise) and the agent's history — a finished session is still findable by work dir or prompt, and reopening it revives the record. So `listAgents`/`listAllAgents` are **live-only**, `listAllAgentsIncludingClosed` serves `/api/agent-history` (no web UI asks for it any more — the pane palette that had a "show closed" mode is deleted; the endpoint stays for CLI and script callers), and `findAgentRecordAny` serves `/api/agent/reopen`, which **revives** the record (`updateAgentPane` clears `closed_at`).
- The whole difficulty is that "no pane" has two causes and only one may condemn a record. Hence: only a **successful** enumeration reconciles (an unreachable herdr keeps returning a PARTIAL listing instead); **per host** always (ids and pane ids are unique only within a host); an **empty** pane list never condemns; records mid-boot are exempt for `agentBootGrace` (a boot holds a visible pane for all but its first instant, so the grace is sized against a lasso restart landing mid-create — unbounded, it stranded a "booting" record for three days); records with no `root_pane` are exempt; and a pane must be missing from **`agentReapMisses` consecutive** enumerations, which covers the last racy window (reopen re-pointing a record at a just-created workspace).
- **Foreign herdr sessions are untouched.** A pane lasso did not create (a long-lived bot like "Clem (OCAI)") has no record to tombstone and is derived from the pane listing on every call, so it comes and goes with the pane it is. A reconcile keyed on lasso's own records would silently drop them — a worse bug than the one being fixed.
- **Which hosts the aggregation queries is `paneTargets`** (extracted so the rule is testable without an ssh fleet). Local, plus every host discovery says is reachable/running/compatible, plus any host still holding a pooled connection — **except one whose probe has SETTLED negative** (`State == ""`, so the booleans are authoritative). The pool fallback exists for the *transiently*-failed probe, where a live socket is the better evidence; it must not outrank a settled verdict, because a machine that has gone away (asleep, off the tailnet) keeps its pool entry long after it stops answering, and dialing through it bought nothing but `paneHostTimeout` of dead air on every poll. One offline Mac was costing `/api/all-panes` **12s**, which is the whole latency of every caller of it — the reaper's pass and each MCP `list_agents`.
- **The fan-out must fit in one wave.** `paneHostConcurrency` (16, matching `hostProbeConcurrency`) is deliberately above the fleet size: the semaphore is taken *before* each host's deadline starts, so with fewer slots than hosts a stalled host does not merely cost its own `paneHostTimeout` — it postpones everything queued behind it, turning one dead box into a multiple of that timeout. `paneHostTimeout` is 10s, just past the `ConnectTimeout=8` that bounds a cold redial: waiting longer cannot rescue a host whose dial has already given up. A host that overruns degrades to its last-good panes and its dial finishes in the background, so the next poll (1.5s TTL) finds it warm.

## File viewer host (`src/panehost.go`, `src/agentcwd.go`, `src/clientmachine.go`)

The sidebar (Files tree, viewer/editor, Diff) follows the FOCUSED pane — its cwd *and* the host that cwd lives on. Those are two different questions once a pane is a window onto another box: `ssh <host> herdr agent attach <name>` (what a fleet attach script runs) and `herdr --remote <host>` both put a remote terminal inside a local pane, and every cwd herdr can report for it is the ssh client's — `/home/stephan` on titan for an agent working in `/home/dev/projects/norm` on norm. The viewer browsed the wrong machine outright.

`activeCwd` (agentcwd.go) now answers `(cwd, source, host)`, and asks about the hop first: `paneForeground` fetches `pane.process_info` once, `paneSSHHop` reads its foreground argv as an attach, and `remoteAttachCwd` asks THAT host's herdr where the attached pane is working (`agent.list` for a named agent, the focused pane of `pane.list` for a session-level attach), resolving the far side with the same precedence as a local pane — harness transcript over SFTP, then herdr's cwds. `Active.CwdHost` carries the answer to the browser as `cwd_host`, and `CwdSource` is prefixed `ssh:` when the far side answered.

- **Only a herdr ATTACH counts.** A plain `ssh host` shell has no far-side pane to ask about — nothing on either end knows where it has cd'd to — so it keeps the local answer. Same for `herdr agent list` and friends: a one-shot remote command is not a window. A false positive repoints the viewer (and its editor's saves) at another machine, so `hostAliasFor` also refuses any destination that isn't a host lasso may drive, and a named agent that is gone resolves to nothing rather than to some other pane. An attach may name a *pane id* rather than an agent, so `attachedPane` falls through to `paneByID` when herdr's `agent.list` carries no row for the target.
- **Every sidebar endpoint takes a host.** `/api/files`, `/api/file`, `/api/diff`, `/api/diff-file` (`?host=`), `/api/file-write`, `/api/file-delete`, `/api/file-rename` (a `host` body field) and `/api/file-upload` (a `host` form field) all resolve through `namedHostBackend`, and tilde-expand against THAT backend. The diff helpers take a `Backend` for the same reason — there is no active-backend `gitOut` any more. Half a cutover here means an editor saving to the wrong machine.
- **`namedHostBackend` short-circuits the DEFAULT host.** An empty selector, or one naming `defaultBackend().Name()`, resolves to that backend itself — the connection we already hold — rather than dialing the pool for the same box; anything else passes the `hostAllowed` gate (502 `host "x" not available`) and comes from the per-host pool, which holds exactly one connection per host shared by every tab on it. `setDefaultBackend` and `hostBackendFn` are the two seams handler and feed tests use to stand a fake fleet up without an ssh master (`diff_test.go`, `filehost_test.go`, `hostfeed_test.go`).
- **A host selector must not blur "no repo" into "no host".** `gitErrNoRepo` classifies the `rev-parse` failure: a plain directory answers 200 `isRepo:false`, while a transport failure stays 502. With `be` now resolved per request, that distinction carries the extra weight of telling a reachable host's non-repo directory from an unreachable host — collapsing them would report a broken remote as a clean tree.
- **The browsed host is UI state, not a live read.** `FilesTab` keeps `curHost` beside `curPath`: both track the focused pane while "follow" is on and freeze together the moment the user types a path or navigates. A host change re-roots even at an identical path (the per-directory caches are cleared first, so one host's listing is never shown for another's), and an open `FileViewer` keeps the host it was opened on — `FilesPanel` captures `{path, host}` together — so focus moving on doesn't redirect a save. `useDiff` keys on `cwd_host`, not the tab's host.
- **The tab's host is untouched.** This resolves where the pane's *work* is; the terminal, host switcher, and creator still follow `Active.Host`. Reading a remote pane's cwd must not move the tab onto that host.

### herdr's saved machines (`src/clientmachine.go`)

herdr 0.9's **machines** are the fourth shape of "the screen is another box", and the only one with no pane to read: one herdr client holds an ssh bridge per saved machine (`herdr machine list`) and draws whichever is selected, while every server involved — including the local one lasso polls — stays unaware. The socket API carries no machine method and no machine field (protocol 22), and herdr's own docs say selecting a machine "does not retarget CLI commands running in an existing pane". So a tab showing ticket500's session still answered every question with the LOCAL herdr's focused pane: the Files sidebar browsed titan, and a pasted screenshot was written to a machine the agent reading it cannot see — an omp agent on ticket500 told to open a `/home/stephan` path that only exists on titan.

The client's selection is the one thing it leaves behind: `~/.local/state/herdr/client/endpoint-selection.json` (`{"version":1,"selected_profile":<id|null>}`, null meaning Local), written within a second of the switch, with `endpoints.json` beside it holding the profiles that id resolves through. `clientMachineHop` reads the pair and hands `activeCwd` the same `sshHop` an attach produces (host set, agent empty — a machine shows that server's own focused pane), so `remoteAttachCwd` resolves the far side exactly as it does for a session-level attach. `CwdSource` is prefixed `machine:`.

- **It outranks the pane, and is asked first.** A selection replaces the whole screen, so the pane `activeCwd` was called for is not even visible — unlike an ssh-attach hop, which is a property of the pane on screen.
- **Only the `local` backend can have one.** Every ttyd lasso spawns runs on lasso's own box, so a tab on a remote host is a `herdr --remote <alias>` client: a standalone attach pinned to one server, with no machine sidebar. Both clients run on the same box and therefore share one selection file, so honoring it for a remote tab would point that tab at whatever machine the LOCAL terminal happens to be showing.
- **A disabled profile, or one naming a non-default remote session, is refused.** Disabled means not connected, so it cannot be on screen; a named session is a herdr server lasso does not talk to (a host backend dials that host's *default* socket), so its panes are not the ones we would resolve there.
- **Every failure is silent and keeps the local answer** — a missing, unreadable or unparseable file, an unknown id, a target `hostAliasFor` won't drive. Being wrong here writes a file to the wrong machine, so nothing is guessed.
- **Two limits worth knowing.** The file belongs to the machine, not to one client: two herdr clients open on different machines share it and the last to switch wins. And a dead client leaves its last selection behind until the next one rewrites it. Neither can produce a path on a host lasso cannot reach, and both cost the same paste that was already wrong.
- **The selection is not a pane list.** lasso's sidebar, ⌘K and the creator still show the tab's host, so clicking a local pane there while a machine is selected focuses something the terminal is not displaying. That predates this; the cwd resolution deliberately follows the screen, since that is what a paste is aimed at.
- **Latency is ~1s of cache plus the feed's poll.** A machine switch fires no event on the local herdr, so nothing pushes it — `clientSelectionTTL` (1s) and the host feed's `pane.list` poll bound how stale `cwd_host` can be right after a switch.
- **herdr 0.9.1's `--machine <label-or-id>` prefix changes none of this, deliberately.** It forwards `workspace`/`tab`/`pane`/`agent`/`worktree` CLI commands to a saved machine's session over non-interactive ssh, which is the same JSON API lasso already reaches directly through its own per-host connection pool (`namedHostBackend`) — one pooled master per host, shared by every tab, against a socket lasso can also SFTP through for transcripts and file reads. Routing lasso's calls through a herdr CLI subprocess per request would trade that for a process spawn and a fresh ssh dial, and the selector is a herdr *profile* label rather than an ssh-config alias, which is not the identity lasso's hosts, scopes and agent records are keyed by. The socket API still carries no machine method and no machine field in protocol 22, so the selection file remains the only way to learn what a client is drawing.

## Chat view (`src/chatview.go`, `src/web/src/components/ChatView.tsx`, `src/web/src/components/AgentSidebar.tsx`, `src/web/src/components/AgentPicker.tsx`, `src/web/src/components/AgentParts.tsx`, `src/web/src/components/NewDialog.tsx`, `src/web/src/lib/agents.ts`)

The terminal column's other half: herdr's focused pane rendered as a conversation, so a session is readable and answerable from a phone. It is an **overlay** over the terminal iframe, which stays mounted and sized underneath — a swap would refit the shared pty to nothing and reflow every other pane. That is also what makes it the phone's way to type: the input dial lives inside that iframe, so the overlay puts it out of reach, and the footer toggle that opens the chat is `md+` only — on a phone the way in is the chat button the dial carries above its root (`.dial-chat`, a dedicated control rather than an arc target: entering the conversation is a destination, not one of the terminal's input controls, and 44px against the root's 58 so it does not read as a second dial). Read-only over `/api/chat`; the composer posts to `/api/chat/send`, which types into the pane the transcript belongs to.

Rows come from the agent's **transcript file**, never from the PTY — a file the agent appends to, so nothing pushes it and the view polls (2s, paused in a hidden tab), paging backwards by byte offset. Resolution starts at the TAB's host (`reqHostBackend`) and follows the same two hops the file viewer does (`chatScreenPane`, below), deliberately NOT `cwd_host`: the chat is about the pane herdr itself is DRAWING, while `cwd_host` is where that pane's *files* live.

- **The pane on screen is not always the tab host's** (`chatScreenPane`). A chat resolved against `reqHostBackend` alone is right for an ordinary pane and wrong for both of the ways another machine ends up on screen — the same two `activeCwd` already resolves. A **machine** selected in the terminal's own herdr client (`clientMachineHop`) draws another server's whole session, so the local herdr's focused pane is not even visible: the chat showed a stranger's conversation and the composer typed into a pane nobody could see. An ssh **attach** (`paneSSHHop`) puts a remote pane inside a local one, so herdr names a session whose log is on the far host: every such pane read "This session's transcript is not on this host yet." about a file that was never coming. Both now resolve through `hopPane` — the far side's backend plus its pane — and `serveChat` rebinds `be` to it, so the pane listing, the agent records, the stat and every byte of the transcript come from one host. The payload's `host` is that host, which is what makes the composer, the ask answerer, the pane close and a relative image path in the prose all address the machine the agent is actually on.
- **A pane id is never carried across a hop.** herdr's ids are unique only within one server (`wQR:p1` exists on every machine that has been up a while), so looking the browser's local id up in a remote listing is a coin flip between the right pane and a stranger's. The far side is addressed the way the hop names it: the attached agent, or that server's own focused pane.
- **The two hops degrade differently, and deliberately.** An unreadable MACHINE is a note (`Can't read <host>'s session.`) rather than a fall back to the tab's own focused pane — that pane is not what the terminal is drawing, so falling back is the bug, not a safe degradation, and the composer is dropped with it. An unreadable ATTACH keeps the local pane, because the local pane IS the window the reader is looking at and typing into it still reaches the far side over ssh.
- **herdr reports a session two ways, and only one of them is a path.** omp gives `kind=path` — an absolute `.jsonl`, used as-is. Claude Code gives `kind=id`, and that is the whole reason this needed its own resolution: the id is looked up at `~/.claude/projects/<slug>/<id>.jsonl` on the pane's own host, `slug` being the pane's cwd with every non-alphanumeric character turned into `-` (claude's own scheme), a scan of the project directories as the fallback when the cwd cannot be guessed. So a claude pane reads its log over SFTP on a remote box exactly as an omp one does. Before this, every claude pane answered "no session" while its transcript sat on disk.
- **A session lasso cannot resolve gets a note, not silence**, and a value that is not an absolute `.jsonl` is refused outright — it reaches a filesystem read on a machine lasso may not be browsing. **An empty view is either a WAIT or a verdict, and the payload says which** (`starting`). A newly created agent spends its first seconds with no session for herdr to report — the CLI is still starting in the pane — and then with a session whose log is not on disk yet, and both read as "No agent session in this pane." about an agent the reader had just asked lasso to create. `paneBooting` claims the session-less pane, and it can only do that from lasso's OWN record (herdr reports an agent in the pane either way; the records come in as an argument so the rule is testable without a db); the log-not-written case needs no record at all, since herdr named a transcript and that transcript is coming. The view shows the orb for anything flagged `starting` and a plain sentence otherwise — so a pane lasso never created, and one whose boot finished long ago (`chatBootGrace`), keep the note that promises nothing.
- **Claude's log is not omp's, and `parseClaudeTranscript` is where the difference lives.** The record TYPE is the role, and a plain user turn's content is a bare string rather than a block list; a tool result is a block on a USER record instead of a message of its own, so it is paired by `tool_use_id` and buffered when the call it answers sits in an older page (the same forward-result window omp needs, in claude's shape); `usage` sums input plus both cache directions; the title is the session's own `ai-title`; `stop_reason` is what decides "working".
- **Subagent traffic is a different conversation, and claude shares the file with it.** Its records are flagged `isSidechain` inside the parent's log (and also written to `<session>/subagents/*.jsonl` beside it, which are entirely sidechain and so parse to nothing), so the parent's view shows the Task card and its result rather than a subagent's reasoning spliced into the middle of it.
- **A turn that was only a pasted screenshot says so.** It carries no text, so without a row the conversation reads as if that message — and the answer to it — came from nowhere.
- **The composer is three-valued on purpose** (`confirmed`/`refused`/`uncertain`). A composer that clears its draft on "uncertain" loses a message; one that retries can duplicate a turn that did land. Neither is a call the server can make for the human. **⌘Enter sends and a bare Enter breaks the line** — it was the other way round, which made every paragraph break a sent message in a field whose whole purpose is prompts written as paragraphs; with the break on Enter, Shift+Enter breaks it too, so a terminal user's habit still works. The button stays the phone's submit, since a software keyboard has no ⌘.
- **The chat's left sidebar lists the FLEET's agents, and the footer's left-hand toggle opens it** (`AgentSidebar.tsx`). That one button means two different things, because the two views have two different left sidebars: in the TERMINAL it sends herdr its own `toggle_sidebar` chord (`lib/terminal.ts:toggleHerdrSidebar` — the default `prefix+b`, since herdr's socket API has no method that opens or closes its sidebar and reports no state for it either, which is why the button is an action there and never an indicator), and in the CHAT it toggles lasso's own panel with a real `aria-pressed`. The panel shows agents ONLY — a pane with no agent is a shell, and the chat cannot display one — one row per conversation **across every connected machine**, this tab's own host first and the rest in name order. That machine is a chip on every row rather than a field of the truncated line, because with the fleet in one list it is what tells two same-named agents apart; next to it sit the harness and the worktree, and above them the name (workspace → pane label → tab → terminal title, herdr's own precedence) with the status, which gets a word for the two states a human acts on (`working`, `blocked`) and a plain dot for the rest. Everything about a row is shared by both surfaces — `AgentLines`/`AgentStatus` in `AgentParts.tsx`, the list and its naming in `lib/agents.ts` — and a row's identity is HOST + pane id (`paneKey`), since herdr's ids are unique only within a host.
- **Below `md` that list is a SHEET instead of a column** (`AgentPicker.tsx`), opened by an agent glyph at the top right of the chat's own header — not a layout glyph, because what it opens is agents to pick from and whether they land in a stack or a grid is the screen's business, not the button's. One column on a phone, two as soon as they fit (`sm:grid-cols-2`), since a tile holds a name, a machine, a worktree and a status and none of those grow with the viewport. Both surfaces render one list from **`lib/agents.ts`** (`useAgents` + `agentName`/`agentSub`, with the marks in `AgentParts.tsx`): they must agree on the naming, the status vocabulary and the address, and they are never both on screen — the column is `max-md:hidden` and the button is `md:hidden`, so exactly one is reachable at any width. The sheet is an overlay INSIDE the chat (its root carries the `relative`), closes on Escape or its ✕, and dismisses as it focuses — the conversation it lands on is the answer to the tap.
- **The chat header is the whole chrome below `md`, and it carries the creator.** The title takes the left edge — and it is herdr's **workspace label**, the name lasso's auto-titler wrote from the agent's prompt and the same one the agent panel lists it under; the fallbacks are the harness's own session title and then the pane's own title (`workspaceLabel` in main.go; `~` does not count, being herdr's placeholder for a workspace it was never given a name for, which is a cwd rather than a name — note the pane title is seeded first and the session title overrides it, so the effective order is label → session title → pane title). A fresh agent with no label and no session title shows the slug that every surface used to — the unique identifier this ordering exists to keep out of a header. The right holds one glyph below `md` — a menu titled "Chat actions", whose items are Agents, Sidebar, Terminal, New agent and Close pane, because that many icons would crowd a phone's title row and a menu can name what a glyph only implies — and at md+ just the close, since the footer already carries Agents (its left-hand toggle), Sidebar, Terminal and New while nothing anywhere closed a pane, and the chat is where you are looking at the pane in question. **Sidebar is an OPEN, not a toggle** (`App.tsx:openSidebar`): below `md` that panel overlays the whole screen, so this header only exists while it is collapsed, and until this item there was no route to it from the chat at all on a phone — the footer is `md+` and the input dial that carries the `sidebar` command lives inside the terminal iframe the chat covers. It stamps `markSidebarIntent` like ⌘\ does, being a human moving the synced layout. Its return path is the panel's own ✕ (`closeSidebar`), which hands the keyboard back to the terminal **only when the terminal is what it uncovers** — over the chat the iframe is hidden, so focusing it would pop a phone's keyboard for a surface nobody can see and aim the next keystrokes at herdr instead of the composer. **Closing asks first** (`AlertDialog`, beside the agent sheet): it is herdr's own `pane.close`, which is what ends the agent in that pane — there is no softer "detach" — and on a phone it is two taps into a menu, so it is confirmed rather than done. lasso navigates nothing afterwards: the chat follows herdr's focused pane, so the view has already moved on by the time the pane is gone. The chat's creator is `agentsOnly` (`NewDialog`): no mode tabs, title "New agent", because the chat reads an agent's session and a bare shell has none to show. A created agent is focused like any other (`focusCreatedAgent`), which is what puts its conversation on screen with no view change — the create path writes `leftView` nowhere.
- **Dismissing the creator from the chat does not hand the keyboard to the terminal** (`NewDialog`'s `onCloseAutoFocus`, on `agentsOnly`): focusing that hidden iframe pops a phone's keyboard over the view the user just returned to, and aims a desktop's next keystrokes at a terminal nobody is looking at — the same reason entering the chat blurs it. It drops focus instead, so the composer takes it on the next tap, as it does after a pick in the sheet. Everywhere else a dismissal still returns the keyboard to the terminal. **`⌘I` is the one shortcut that leaves chat**: a new terminal is not something the chat's dialog can make, so it hands the screen back to the terminal first and opens the creator there, rather than answering a terminal shortcut with an agent form.
- **Selecting an agent moves the TAB when it lives elsewhere, then focuses it** — `moveTabToHost`, then `api.focus` with the row's **`pane_id`** (herdr's `pane.focus` focuses the pane's workspace, its tab and the pane, so a split tab's two agents — two rows here — are individually reachable; `workspace_id`/`tab_id` ride along only as the server's fallback for a pane closed since the listing, and focusing the pane is also what marks it SEEN, clearing a finished agent's Done badge). The order is the whole thing: the focus call is addressed to the host the tab is on, and the chat follows that host's focused pane, so attaching after focusing would land the focus on a machine the chat is not showing. It is the same two steps the creator's success path takes, and the chat then follows the pane over SSE, so the highlight is never a second source of truth: a row is current because herdr says that pane is focused, with the pick standing in until the host feed's event or 2s poll catches up. `panes_rev` covers this tab's host (create/close/rename) and a 5s poll covers the other machines plus the one thing no layout revision carries, an agent's status; a host whose enumeration failed contributes no rows and says so at the end of the list rather than letting its agents look deleted.
- **The panel takes width from the CHAT, not from the terminal** — it is a flex column inside the chat overlay, which already sits over a terminal that stays mounted and sized. A real panel there would refit the shared pty every time someone opened a list, reflowing every other client's herdr for a panel nobody in those panes can see. Per-TAB for that reason (and unlike the right sidebar's synced layout). Below `md` it is not hidden but *replaced*: the footer that opens it does not exist there, so the sheet above is that width's way to the same list.

## Browser tab (`src/web/src/components/BrowserTab.tsx`)

It is **client-side only** — a URL bar and an iframe. A bare port (`5173`, `:5173`, `localhost:5173`) resolves to `http://<location.hostname>:<port>`; anything else is used verbatim. There is no backend: no `/api/preview`, no `tailscale serve` forwards, no Cloudflare wildcard demux (`lasso devproxy`), no Access-cookie priming. All of that existed and was **deliberately removed** — it was a lot of per-deployment wiring (DNS wildcard, tunnel ingress, an Access app, a supervised daemon, a `-preview-public-domain` flag) to work around a browser rule, and the rule wins anyway.

- **What the browser allows is the whole contract.** An HTTPS origin can't frame an `http://` dev server (mixed content) and a public origin can't frame a private/tailnet one (Private Network Access). Both cases are detected and reported in the tab, with open-in-new-tab as the out. Don't reintroduce a tunnel to dodge them.
- `probeReachable` (a `no-cors` fetch), not the iframe's `onLoad`, is the failure signal: a PNA-blocked frame still fires `onLoad` while rendering blank.

## Notifications (`src/notify.go`, `src/webpush.go`, `src/notifywatch.go`, `src/notifycli.go`, `src/web/public/sw.js`, `src/web/src/lib/push.ts`)

An agent that blocks — a tool approval, omp's plan gate, codex's "Action Required" — stops until a human answers, and nothing in lasso could tell that human unless they were already looking at a screen. `notice`/`notifyUI` is an SSE toast, so it reaches open tabs only. This reaches a locked phone.

The split is deliberately two registries, so the second of either costs nothing: a **kind** says what happened (`notifAgentBlocked`, inferred by the watcher; `notifAgentMessage`, an agent deliberately pinging its human; `notifTest` for the Settings button), a **transport** says how it reaches a human (`webPushChannel` today). Nothing above the transport knows what Web Push is — a `notification` carries text, a collapse tag, and the host the event happened on, never endpoints or keys.

Two delivery forms, because the callers differ in what they can wait for: `publishNotification` is fire-and-forget for the poll loop, `deliverNotification`/`notifyNow` are synchronous and report what took it. An agent that pings its human MUST get that answer — "sent" when nothing is subscribed is the one reply that would make the feature worse than not having it — so both the `notify` tool and the Settings test button go through `notifyNow`, and `lasso notify` exits non-zero on `sent:false`.

- **Web Push, standard library only** (`webpush.go`). RFC 8291's derivation over RFC 8188's `aes128gcm` framing, with an RFC 8292 (VAPID) ES256 JWT; `crypto/ecdh`, `crypto/hkdf` and `ecdsa.ParseRawPrivateKey`/`PublicKey.Bytes` cover all of it since Go 1.24, so there is no dependency to audit. `sealWebPush` takes the salt and the ephemeral key as parameters purely so the RFC 8291 §5 test vector reproduces byte for byte (`webpush_test.go`) — that vector is the only way to prove the derivation without a phone.
- **The VAPID `sub` claim is the subscription's page origin**, and that is not cosmetic: Apple answers **403 BadJwtToken** for anything that is not a `mailto:` or a full https URL, which is exactly what the `mailto:lasso@<hostname>` a self-hosted server would otherwise invent looks like. Verified against the live `web.push.apple.com`: an origin-derived subject gets through to a `BadWebPushToken` (i.e. the JWT and the encrypted body were accepted, only the fabricated device id was not), while the hostname fallback is refused outright. `LASSO_PUSH_CONTACT` overrides; the fallback is only reachable for a non-https (loopback dev) origin, which is never Apple's service.
- **The VAPID keypair is generated once into `settings.push_vapid_private`** and must then never change: the browser pins the public key into every subscription it creates, so a new key silently invalidates every registered device. It is stored usable (not hashed) because it has to sign unattended — the same trust model as the OAuth client secret already in that db.
- **404/410 is the only failure that deletes a device.** That is RFC 8030's "this subscription no longer exists". A 403 (our credentials) or a 5xx (their service) is recorded on the row and retried — pruning on those would delete healthy devices over a transient outage, and the Settings list shows `last_error` precisely so a device that stopped working says so instead of looking identical to one that works.
- **The watcher polls, and only when something is listening** (`notifywatch.go`). It reuses `panesSnapshot`, not its own enumeration: that aggregation already has per-host deadlines, already degrades to last-good panes, already resolves the status lasso considers authoritative (herdr's, corrected by title reads and the omp plan gate), and its 1.5s cache makes a poll that lands near a browser's ⌘K refresh free. `notifyEnabled()` is checked first, so with no device subscribed the whole feature costs one `COUNT(*)` against a local sqlite file every 10s and touches no host.
- **Detection is a transition into `blocked`**, per pane, with a 5-minute floor per pane (`notifyRenotify`) so an agent that answers one approval only to raise the next buzzes once. A pane's remembered status outlives its disappearance by `notifyForget` (10m), so an unreachable host coming back is not read as every one of its agents having just blocked. Deliberately **no first-poll baseline**: an agent that blocked while lasso was restarting, or while notifications were being switched on, would otherwise never be announced at all — which is the hole this exists to close.
- **A pane is keyed by host + pane id** (`notifyPaneIdentities`), since pane ids are unique only within a host. That keying is also what makes the aggregation's last-good fallback inert: a stale listing re-states keys the watcher already recorded instead of reading as new.
- **The notification names a host, never a pane.** Opening it lands the tab on the right machine and stops there, because herdr's focus is one global per session shared with the TUI and every other client — a link that focused a pane would move it for everyone (the same reason `lib/url.ts` keeps focus out of the URL).
- **Everything the service worker needs is in the encrypted payload.** `sw.js` runs with no page and cannot call back into lasso: behind Cloudflare Access an unauthenticated fetch returns a login page. So a payload carrying only an id would be a notification the phone cannot render.
- **The service worker caches nothing and has no `fetch` handler.** lasso is a live view of machines you are driving, so an offline shell of it would be a lie, and a stale bundle in front of a self-updating binary is a support burden with no upside. That absence is also what makes `skipWaiting`+`clients.claim` safe. `/sw.js` is served `no-cache, must-revalidate` (`noStore` in main.go) because it is the one asset whose URL never changes — Cloudflare would otherwise hold an edge copy of it for hours past an update.
- **iOS gates push behind installation**, so `lib/push.ts` reports `needs-home-screen` distinctly from `unsupported` and the Settings section says which. `enablePush` must run straight from the click: Safari only honors `Notification.requestPermission` from a user gesture. A subscription pinned to a *different* server key (a restored db, another lasso) is dropped and re-minted rather than left to throw `InvalidStateError`. Verified end to end in Chrome via CDP `ServiceWorker.deliverPushMessage`: the worker raises the notification, a repeated tag replaces rather than stacks, and an unparseable payload still shows something (a `userVisibleOnly` subscription that shows nothing loses its permission).
- **`lasso notify` is a CLIENT of the `notify` MCP tool** (`notifycli.go`), not a second implementation: one description the model reads, one rule about attribution, one place where "sent" is decided. It was the first CLI subcommand to speak MCP and `lasso mcp` generalized it (they share `dialMCP`); `closeme` deliberately POSTs a plain endpoint instead, because the two commands are different things: closeme is lasso acting on its own agent record, while notify is an agent using a tool, and giving the CLI its own `/api` route is how the two would drift. `LASSO_URL`/`LASSO_LISTEN` locate the server, and it sends `LASSO_MCP_TOKEN` or the `UI_AUTH` basic credentials when either is set (both usually absent, since `/mcp` is open by default).
- **`notify` attributes through `resolveCallerAgent`** — extracted from `whoamiTool` so the sender's name is exactly the answer whoami would give, rather than a second, subtly different resolution. A lock-screen notification is read title-first, so the agent's workspace label ("Port the auth tests") is the title and the message is the body. An unresolvable pane is NOT an error: the message still matters, so it goes out titled "lasso" with the resolution problem in `detail`.
- **A deliberate message carries no tag, so nothing collapses.** The watcher tags per pane on purpose (repeated "still blocked" is one entry); two messages an agent chose to send are two things it said, and folding them would hide the first. That is also why `sw.js` must leave an absent tag absent instead of defaulting to a shared constant — the bug that default would cause is silent.

## `lasso mcp` — the tool surface as a CLI (`src/mcpcli.go`)

`lasso notify` proved the shape and `lasso mcp` is its general case: every registered MCP tool as a shell command, over the same endpoint, with the same credentials and the same one-shot session (`dialMCP`, shared by both). `lasso mcp` lists, `lasso mcp <tool> -h` shows one tool's flags, `lasso mcp <tool> [flags]` calls it. An agent with lasso's MCP server configured calls the tools directly; one that only has a terminal — which is most of them, most of the time — types this and gets the same behavior from the same descriptions.

- **The flags are built from the schema the SERVER advertises, never from a table in the file.** The binary you type is not necessarily the binary answering (a `lasso update` since the shell started, `LASSO_URL` pointing at another box), and a hand-kept copy of the tool list is precisely the drift notify was written as an MCP client to avoid. A tool added to `mcp_tools.go` is on the CLI the moment the server restarts, with no second place to edit — which is also why `mcpcli_test.go` asserts against the real `/mcp` handler rather than a fixture.
- **An omitted flag is ABSENT from the call, not a zero value.** The tools distinguish the two (an empty `host` means "search every host I may reach", not "the host named empty string"), so `argFlag` records whether it was set at all and only set flags reach `Arguments`. Required fields are checked locally purely to save a round trip — the SDK validates the same schema server-side, so this mirrors its answer rather than inventing a stricter one.
- **Both spellings resolve, for the tool name and every flag.** The model-facing docs say `read_agent`/`agent_id`, every CLI listing says `read-agent`/`--agent-id`, and refusing whichever one someone has in front of them is a papercut with no upside. The kebab alias is registered against the *same* `argFlag`, so it is one field, not two.
- **A blocking tool's own timeout outranks the transport deadline** (`toolSelfTimeout` + `mcpCallSlack`). `wait_agent` asked to wait three minutes, cut off at the CLI's two, reported a bare "context deadline exceeded" about a call that was going fine. The root context therefore carries no deadline — the session has to outlive the setup phase — and each phase takes its own child: `-timeout` for dial/list, and for the call whichever is longer of that and the tool's own timeout argument plus slack. The argument is recognized by name and unit suffix rather than a list of tools, so it can only ever *extend*, never shorten.
- **`-json` is accepted after the tool name as well as before**, unless the tool's own schema claims that name. Parsing stops at the tool name (that is what splits our flags from its), so a global would otherwise have to lead — the exact papercut mcp2cli has.
- **A parse error the flag package already printed is not printed twice** (`errFlagReported`): a second copy under a screen of usage reads as two different problems. Explicit `-h` prints to stdout and exits 0, which is what tells it apart from a usage error on stderr exiting 2; only a LEADING help token counts, since a value further along may legitimately be the string `-h`.
- **Structured output is the payload when there is one.** Every lasso tool has a typed `Out`, so the text content beside it is the same data rendered for a model and printing both would double every answer. Indented on a terminal, compact when piped, so `| jq` needs no flag. Exit 1 when the tool itself refused (distinct from a transport failure, which exits 1 through `fatal` and prints no result); exit 2 for a usage error.
- **`notify` and `closeme` keep their own subcommands.** notify's exit code is a contract (non-zero when nothing was listening) and it reads a piped message; closeme resolves `$HERDR_PANE_ID` for you and deliberately POSTs a plain endpoint. Both are the short spelling of a call this can also make the long way.
